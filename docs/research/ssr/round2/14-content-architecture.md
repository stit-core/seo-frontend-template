## 1. TL;DR

1. **Дефолт источника контента — git-коллекции с Zod-схемой**, а шов `ContentSource`
   (`fs` | `http`) закладывается сразу: у экосистемы нет CDN и нет CI-раннера, поэтому
   любая CMS — это плюс контейнер, плюс БД, плюс бэкап и плюс публичный роут на том же
   VPS. Миграция «git → CMS» должна стоить правку конфига и одного адаптера, а не
   переписывание страниц (§2.1.1–2.1.2, §2.1.5).
2. **Ландшафт self-host CMS в 2026 сместился не в нашу пользу.** Directus с v12 ушёл на
   собственную MSCL (не OSS): бесплатный Core — **3 места и 25 коллекций**, всё сверх —
   лицензионный ключ (бесплатный Open Innovation Grant при выручке < $5 млн и < 50
   сотрудников, 5 активаций, **продление раз в год**). Для «поставил заказчику и забыл»
   это дисквалифицирующее свойство. Дефолтом остаётся **Payload 3.89 (MIT)** или
   **свой Go-бэкенд экосистемы**; SaaS (Sanity/Contentful) отклонён по умолчанию —
   трансграничная передача ПДн и оплата из РФ (§2.1.5, §2.7.3).
3. **Для «редактор не разработчик» самый дешёвый ответ — Decap CMS поверх собственной
   Gitea**: у Decap есть backend `gitea` с PKCE прямо в браузере (без OAuth-прокси),
   требует Gitea ≥ 1.20, а в `corp-infra-template` уже стоит **Gitea 1.26.1**. Ноль новых
   контейнеров. Keystatic умеет только GitHub/Keystatic Cloud и для нашей Gitea не
   подходит (§2.1.5).
4. **Развилка «prerender ⊥ runtime `SITE_URL`» решается режимом D** (рендер на запрос +
   кеш HTML в процессе), а штамповка плейсхолдера при старте (C) — включаемая
   оптимизация. Абсолютные URL живут только в `<head>`, JSON-LD, фидах и sitemap; в теле
   документа — корневые относительные (§2.2.2–2.2.3, инвариант C-6).
5. **Markdown компилируется на билде, страница собирается на запрос.** Контент-индекс
   (frontmatter + пути + даты + `translationKey`) — единый источник для списков, sitemap,
   RSS, поиска и hreflang; ошибка Zod-схемы = красная сборка (§2.2.6, C-1/C-2).
6. **Метаданные — данные, а не разметка**: три уровня (идентичность сайта → `docs/stack/seo.md`;
   страница → frontmatter; структура → иерархия маршрута), одна функция `metaFromDoc`
   и unit-гейт на её выход. Видимые хлебные крошки и `BreadcrumbList` собираются из
   одного массива (§2.8).
7. **i18n: параллельные каталоги + явный `translationKey`; fallback-политики нет** —
   непереведённая страница не публикуется под чужой локалью (404, а не дубль); hreflang
   выводится только из фактического набора переводов (§2.9, C-13/C-14).
8. **Редиректы — это данные** (`content/redirects.yaml`), применяемые сервером как
   301/410 одним хопом; `meta refresh` как механизм редиректа запрещён — у Astro статические
   редиректы при `astro build` вырождаются именно в него (§2.10.3, C-11/C-12).
9. **Бюджеты, от которых считается всё остальное**: 0 КБ JS на контентной странице
   (потолок 30 КБ на острова), HTML ≤ 100 КБ, CSS ≤ 15 КБ gzip, шрифты ≤ 60 КБ,
   LCP-картинка ≤ 150 КБ AVIF, TTFB кеш-хита ≤ 50 мс. Медиана веба-2025 — 2,1 МБ и
   646 КБ JS: цель — быть в 5–10 раз ниже, и главный вклад даёт не героизм, а отсутствие
   JS-фреймворка на контентных страницах (§2.11).
10. **Шрифт по умолчанию — не Inter.** Кириллический сабсет variable-шрифта стоит
    10–20 КБ WOFF2, и выбор упирается не в вес, а в наличие настоящего курсива: у
    «кириллица-первых» Manrope / Golos Text / Onest / Geologica его нет вовсе.
    Рекомендация: текст — **Wix Madefor Text Variable** (13,8 КБ cyrillic, `wght 400–800`,
    есть italic), акциденция (опционально) — **Onest** или **Golos Text**. Astro Fonts API
    стабилен, провайдер `fontsource`, но `subsets` по умолчанию `["latin"]` — обязательный
    override (§2.4.2).
11. **Юридический минимум РФ вытекает не из «закона о куках» (его нет), а из 152-ФЗ**:
    страница политики обработки ПДн обязательна прямой нормой (ст. 18.1 ч. 2), уведомление
    РКН о намерении обрабатывать ПДн нужно практически всем с 01.09.2022 (266-ФЗ от
    14.07.2022), согласие должно быть «конкретным, предметным, информированным, сознательным
    и однозначным» (ст. 9 ч. 1). Штрафы после 420-ФЗ (в силе с 30.05.2025): нет политики —
    до 60 тыс. ₽ для ЮЛ, обработка без согласия — 300–700 тыс. ₽, неуведомление РКН —
    100–300 тыс. ₽, нарушение локализации — 1–6 млн ₽ (§2.7.3).
12. **Третьи стороны — главный источник и веса, и юридического риска.** Измерено
    2026-09-16: Яндекс.Метрика `tag.js` — **95,8 КБ** по проводу (292 КБ raw), это в 3 раза
    больше всего бюджета JS страницы; reCAPTCHA — **357 КБ**; hCaptcha — **102 КБ**;
    Turnstile — **28 КБ**; SmartCaptcha — **35,6 КБ**. При этом `googletagmanager.com` и
    `google-analytics.com` с российской машины **не открываются вообще** (TLS-сессия
    рвётся сразу после ClientHello), тогда как `google.com`/`gstatic.com` доступны —
    GA4 для РФ-сайта это не «вторая система аналитики», а сломанный по умолчанию
    компонент (§2.7.4–2.7.5).
13. **Доставка заявки: Telegram технически жив, продуктово — нет.** `api.telegram.org`
    с сервера доступен (проверено), лимиты Bot API 10.3 — ~30 сообщений/с и 20/мин в
    группу, при перелимите 429 + `retry_after`. Но с 10.02.2026 РКН публично и поэтапно
    ограничивает Telegram по всей стране, и получатель заявки может её просто не увидеть.
    Параллельно Mail.ru (12.06.2026) и Яндекс (29.06.2026) закрыли SMTP/IMAP на бесплатных
    тарифах. Вывод: шов `FORM_DELIVERY=telegram|smtp|backend` — обязателен, каналов
    настраивается **минимум два**, и заявка складывается в durable-очередь на диске
    до подтверждения доставки (§2.6.5).
14. **A11y-гейт строится на axe-core 4.13**, но с двумя оговорками: у `vitest-axe` нет
    стабильного релиза с 2022 года (живёт тег `pre` = `1.0.0-pre.5`), а `@lhci/cli` 0.15.1
    тащит внутри **Lighthouse 12.6.1** при актуальном 13.4.1 — поэтому LHCI остаётся
    отдельным CI-stage, а не частью `pnpm check` (§2.12.1).

## 2. Findings

### 2.1. Источник контента

#### 2.1.1. Варианты и кому что подходит

Ось решения — **не «git vs CMS»**, а три независимых вопроса: (1) кто автор текста,
(2) с какой частотой публикуют, (3) совпадает ли публикация с релизом.

| # | Вариант | Кто редактирует | Инфраструктурная цена | Публикация = | Когда это правильный выбор |
|---|---|---|---|---|---|
| а | **Git-контент**: Markdown/MDX в репо, типизированные коллекции (Zod) | разработчик или редактор через PR/CMS-поверх-git | 0 контейнеров, 0 БД, 0 бэкапов | новый образ (релиз) | лендинг, корпоративный сайт, доки, блог с 1–20 публикациями в месяц; когда тексты правит тот же, кто правит код, или правки редки |
| а+ | Git-контент **+ CMS-поверх-git** (Decap/Keystatic/Tina) | маркетолог в вебе, коммит делает CMS | 0 контейнеров (UI отдаётся самим сайтом); для Gitea — Decap CMS с PKCE прямо в браузере, OAuth-прокси не нужен (§2.1.5) | новый коммит → релиз | то же, но редактор не умеет в git; **цена** — публикация всё равно требует пересборки образа |
| б | **Headless CMS в self-host** (Payload / Directus / Strapi) | редактор в админке | +1–2 контейнера, +БД (Postgres), +бэкап, +роут `cms.${DOMAIN}`, +обновления | запись в БД → инвалидация кеша сайта | новости/блог с ежедневными публикациями, каталог с товарами, несколько ролей и модерация |
| б− | **SaaS-CMS** (Sanity, Contentful…) | редактор в облаке | 0 контейнеров, но внешняя зависимость | вебхук → инвалидация | **для РФ-заказчика — риск по умолчанию отклонён**: оплата, санкции, доступность, ПДн-трансграничка |
| в | **Свой Go-бэкенд экосистемы** как контент-API (`go-backend-template`, huma/OpenAPI) | админка, которую надо написать | +0 контейнеров (бэкенд уже есть в проекте) | запись в БД → инвалидация | когда контент — это **уже доменная сущность продукта** (товары, объекты, вакансии, врачи), а не «статьи»; когда админка и так пишется |
| г | **Гибрид** | маркетинг — в git, домен — в API | по компонентам | по компонентам | реальный корпоративный сайт: лендинг/о нас/юридическое — git; каталог/новости/вакансии — API |

**Проверяемые факты по кандидатам (версии, лицензии, self-host)** — см. §2.1.5
(подтверждено фетчем npm/доков 2026-09-15).

#### 2.1.2. Рекомендация шаблону

1. **Дефолт шаблона — (а) git-контент с типизированными коллекциями.** Обоснование —
   прямое следствие ограничений экосистемы, а не вкусовщина:
   - **нет CDN и нет CI-раннера** → любая CMS добавляет контейнер, БД, бэкап и ещё один
     публичный роут на том же VPS, который и так тащит сайт; цена эксплуатации ложится
     на владельца проекта, у которого нет ops-команды;
   - **«один образ = один артефакт релиза»** уже принят каноном (`04` §1.1); git-контент
     ровно в него ложится: контент версионируется, ревьюится, откатывается тем же
     `make bump SVC=site TAG=vX.Y.Z`;
   - контент в git **типизируется Zod-схемой** — тот же приём, что в SPA-шаблоне для
     контрактов API (`entities/<name>/model/schema.ts`), то есть это наследование
     привычки, а не новый механизм;
   - предсказуемый рантайм: нет «сайт лёг, потому что упала CMS».
2. **Шов для (б)/(в)/(г) закладывается сразу, а не «когда понадобится».** В `shared/content`
   объявляется интерфейс источника, у которого в шаблоне две реализации:

   ```ts
   // shared/content/source.ts — черновик, фреймворк-агностичный
   export type ContentQuery = { type: string; locale: string; slug?: string;
     tag?: string; page?: number; draft?: boolean }
   export interface ContentSource {
     list(q: ContentQuery): Promise<ContentIndexEntry[]>   // только метаданные
     get(q: ContentQuery & { slug: string }): Promise<ContentDoc | null>
     // для sitemap/RSS/инвалидации
     all(type: string, locale: string): Promise<ContentIndexEntry[]>
   }
   ```
   - `fsSource` — читает **индекс, собранный на билде** (см. §2.2.6);
   - `httpSource` — ходит в CMS/бэкенд, ответ валидируется той же Zod-схемой.
   Переключатель — `CONTENT_SOURCE=fs|http` в runtime config. Это делает миграцию
   «начали с git → выросли до CMS» правкой конфига и одного адаптера, а не переписыванием
   страниц. **[?]** (инженерное решение; прецедент — та же двойственность `API_MODE=mock|real`
   в SPA-шаблоне).
3. **Если заказчику нужна CMS сразу** — рекомендация по умолчанию **Payload** (Node, ставится
   рядом в compose, Postgres, self-host без лицензионных сюрпризов) или, если контент уже
   доменный, — **(в) свой Go-бэкенд**: у экосистемы есть готовый шаблон, OpenAPI-контракт,
   миграции, бэкапы и правила эксплуатации. Второе часто дешевле первого: один сервис
   вместо двух. Конкретика по версиям — §2.1.5.
4. **Sanity/Contentful и прочий SaaS — не дефолт** и требуют явного решения владельца
   (оплата из РФ, доступность, трансграничная передача ПДн — §2.7.3).

#### 2.1.3. Откуда берутся тексты (связь со strategy-репо)

Это тонкое место: соседний `<org>/strategy` — **design-time SoT продукта, но не хранилище
копирайта**, и это зафиксировано его собственным каноном:

- `project/vision.md`: «❌ **Маркетинговая копия для лендинга.** Vision — внутренний
  документ аналитика, не сейлз-материал» **[П]** (чтение
  `business-strategy-template/docs/projects/_template/project/vision.md`, 2026-09-15);
- `project/market.md`: «❌ **Маркетинговая копия** (своя или их). Здесь — наблюдаемые
  свойства, а не позиционирование» **[П]**;
- `screens/` описывает **композицию и облик** (shell → slots → blocks → states), в языке
  дерева `layout:`/`ui:`/`data:`; текст в дереве появляется только как children-строка
  («'Создать'») — это подпись элемента, а не контент страницы **[П]**;
- `fsd/_template/pages.md` — `slug · name · description · screen · path · guard · widgets ·
  features · entities · status`; SEO-полей и текстов нет **[П]**.

Отсюда честное разделение для контентного сайта:

| что | где живёт | кто автор |
|---|---|---|
| какие страницы существуют, кому и зачем | `interface/<surface>/situation.md`, `screens/<surface>/screen.md` | аналитик в strategy |
| какие **типы контента** есть (статья, услуга, кейс, вакансия, FAQ-запись) | `interface/<surface>/data-items.md` → `fsd/<surface>/entities.md` (колонка `source`) | аналитик в strategy |
| маршруты и доступ | `fsd/<surface>/pages.md` (`path`, `guard`) | аналитик в strategy |
| **идентичность сайта** (бренд, дефолтные title/description, OG, JSON-LD Organization) | `docs/stack/seo.md` в сайт-репо | владелец сайта + разработчик |
| **тексты страниц и постов**, их title/description для выдачи, обложки | контент-слой сайт-репо (frontmatter + тело) либо CMS | заказчик/копирайтер/маркетолог |
| режим рендера, кеш, индексируемость маршрута | `docs/stack/rendering.md` в сайт-репо | разработчик |

То есть **strategy даёт скелет смысла, сайт-репо — плоть текста**. Попытка затащить
SERP-копию в strategy сломает его канон (см. цитаты выше) и смешает две скорости
изменения: экран меняется раз в квартал, title лендинга — раз в неделю.

`/scaffold` для контентного сайта читает `entities.md` (какой контент-тип), `pages.md`
(маршрут, guard) и разворачивает: Zod-схему коллекции, страницу списка/детали, запись
в `rendering.md`, заготовку тестов. Тексты он не выдумывает — кладёт `TODO`-frontmatter
и печатает, кому их заказать.

#### 2.1.4. Preview/draft без CDN

Требуется, как только редактор не разработчик. Контракт (прямая калька с
Next.js Draft Mode **[П]** https://nextjs.org/docs/app/guides/draft-mode, версия доки
16.3.5, обновление 2026-06-02 — берём как проверенную временем механику, не как
зависимость):

1. `GET /api/preview?token=<hmac>&slug=<path>` — server route. Токен: HMAC-SHA256 от
   `slug + exp` на секрете `PREVIEW_SECRET`; проверяется срок (≤ 30 мин).
2. Хендлер **сначала проверяет, что `slug` существует в источнике**, и редиректит на
   путь, взятый из найденного документа, а не из query — иначе open redirect (эту ошибку
   Next.js документирует явно: «Redirect to the path from the fetched post, not from
   searchParams, to avoid open redirect vulnerabilities» **[П]**).
3. Ставится httpOnly-cookie `preview=1` (`SameSite=Lax`, `Secure`, короткий `Max-Age`).
4. Любой ответ при наличии cookie: **мимо кеша**, `Cache-Control: private, no-store`,
   `X-Robots-Tag: noindex, nofollow`, видимый баннер «Черновик» с кнопкой выхода
   (`POST /api/preview/exit`). Next.js в том же режиме отдаёт
   `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` **[П]**.
5. E2E-гейт: (а) без cookie черновик отдаёт **404**, (б) с cookie — 200 + `noindex` +
   `no-store`, (в) в sitemap черновика нет.

Для git-контента «черновик» — это `draft: true` во frontmatter (в прод-сборке такие
документы не попадают в индекс контента вовсе, кроме режима preview); для CMS — её
статус записи.

##### Directus v12 — что именно поменялось и почему это важно для self-host у заказчика

Это ключевая находка раздела, потому что Directus три года был удобным ответом на
«нужна админка для контента».

- **Что действует.** Ядро Directus лицензировано **Monospace Sustainable Core License,
  Version 1.0 (MSCL-1.0-GPL)** — проверено чтением `license` в `directus/directus@main`
  [П] https://raw.githubusercontent.com/directus/directus/main/license. Раньше был BSL
  (с апреля 2023), до этого — GPL/MIT-линия; переход на MSCL анонсирован **22.04.2026**
  и приехал с **v12** [П] https://directus.com/resources/directus-v12-license-change.
- **Механика лицензии.** Разрешено всё, кроме *Competing Use* — «making the Software
  available to any party … that competes with the Licensor's commercial offerings of the
  Software itself, where Licensor imposes a license fee» [П] (текст лицензии). Прямо
  разрешены «internal use» и **«professional services … including professional services
  to deploy the Software or host the Software for the licensee»** — то есть студия может
  разворачивать Directus клиенту. Каждая версия автоматически становится **GPL-3.0 через
  4 года** после публикации [П].
- **Ловушка не в тексте лицензии, а в лицензионных ключах.** В том же документе есть
  раздел *Limitations*: запрещено «move, change, disable or circumvent the **license key
  functionality** of the Software» [П]. То есть в v12 появился платный контур, зашитый в
  код. По официальной документации [П] https://directus.com/docs/licensing/overview:
  «Self-hosted instances without a license run on the core tier», а Core по прайсу — это
  **3 пользовательских места и 25 коллекций** (плюс 5 Flows) [П]
  https://directus.com/pricing.
- **Бесплатный коммерческий контур — Open Innovation Grant**: «entities with less than
  **$5M in annual revenue and fewer than 50 employees**» [П]
  https://directus.com/docs/licensing/open-innovation-grant. Ключ выдаётся на **5
  активаций** (локаль/dev/staging/prod одного проекта; агентству — **отдельный ключ на
  каждый проект клиента**), действует **1 год**, продлевается, есть 30-дневный
  grace-период [П].
- **Что это значит для нас.** Схема экосистемы — «студия разворачивает клиенту сервис и
  уходит» — ломается о годовое продление ключа и о привязку ключа к юрлицу заказчика:
  появляется операционная задача, которую некому выполнять (ops-команды у заказчика нет).
  Без ключа сайт-CMS упирается в 25 коллекций и 3 редактора, что для каталога — мало.
  ⇒ **Directus исключается из дефолтов шаблона**; если заказчик уже на нём — фиксировать
  в `docs/stack/content.md` строкой «лицензионный ключ OIG, истекает <дата>, продлевает <кто>».

##### Почему Decap CMS — правильный «CMS-поверх-git» именно для stit

В отчёте 14 §2.1.1 у варианта «а+» стояла цена: «нужен OAuth-мост к git-хостингу».
Проверка показала, что для нашей связки этой цены нет:

- у Decap есть backend **`gitea`**, авторизация — **PKCE прямо в браузере**, внешний
  OAuth-прокси не нужен; в Gitea заводится OAuth-приложение с **снятой** галкой
  *Confidential Client* [П] https://decapcms.org/docs/gitea-backend/;
- требования: **Gitea ≥ 1.20** (Forgejo ≥ 1.21.4 + CORS) [П]; в экосистеме стоит
  **`gitea/gitea:1.26.1`** [П] (чтение `corp-infra-template/compose/gitea.yml:31`) —
  запас большой;
- ограничения, которые надо знать заранее: **git-lfs не поддерживается** этим бэкендом
  [П] (значит оригиналы картинок — обычными файлами в репо либо в MinIO, как и
  решено в §2.3.3), и все редакторы должны иметь push-доступ к репо контента;
- конфиг минимальный:

```yaml
# public/admin/config.yml — черновик
backend:
  name: gitea
  repo: <org>/site
  app_id: <client-id из Gitea OAuth app>
  api_root: https://git.stit.tech/api/v1
  base_url: https://git.stit.tech
  auth_endpoint: https://git.stit.tech/login/oauth/authorize
  branch: main
media_folder: content/assets
public_folder: /assets
```

Цена остаётся ровно одна и она архитектурная, а не техническая: **публикация = коммит =
релиз образа** (риск R-3 из §5.1). Для сайта с правками раз в неделю это нормально; для
ежедневных новостей — нет, и там сразу вариант (б)/(в).

##### Астро-специфика: что вообще значит «подходит как источник для Content Layer»

Content Layer Astro принимает **любой** асинхронный loader, поэтому «поддержка CMS» —
это не бинарный признак, а вопрос «есть ли готовый пакет или пишем 30 строк». Реальная
картина на 2026-09-16: готовый живой loader есть только у Strapi
(`strapi-community-astro-loader` 4.0.0, MIT [П]); у Payload — заброшенный `astro-payload-loader`
0.1.0 (единственный релиз 2025-01-27) [П]; у Directus — только обсуждение, пакета на npm
нет [П]. Практический вывод: **выбор CMS не должен упираться в наличие loader'а** — своя
реализация поверх `ContentSource.http` из §2.1.2 в любом случае надёжнее чужого
однорелизного пакета, и она же даёт Zod-валидацию ответа. **[?]**

##### Почему SaaS-CMS отклонён по умолчанию (аргумент, а не вкус)

Три независимых причины, любой из которых достаточно:

1. **Право.** Контент-редакторы и посетители — субъекты ПДн; передача их данных в
   юрисдикцию, не входящую в перечень стран с адекватной защитой, — трансграничная
   передача по ст. 12 152-ФЗ с обязательным **отдельным уведомлением РКН до начала
   передачи** и правом РКН её запретить; критерии формирования перечня ужесточены
   **265-ФЗ от 26.07.2026** (§2.7.3).
2. **Деньги.** Оплата зарубежной подписки из РФ — отдельная задача заказчика, которая
   повторяется ежемесячно и однажды не решится.
3. **Доступность.** Сайт, чей билд ходит за контентом в зарубежный API, в момент
   блокировки/замедления перестаёт собираться; §2.7.5 показывает, что это не гипотеза
   (домены Google Analytics с российской машины уже не открываются).

Решение — владельца, и оно записывается строкой в `docs/stack/content.md`, а не
принимается разработчиком по умолчанию.

### 2.2. Рендер-стратегия по типу страницы и **развилка «prerender ⊥ runtime SITE_URL»**

#### 2.2.1. Таксономия режимов (четыре, не больше)

Имена — в языке решения, а не в языке фреймворка (в `docs/stack/rendering.md` они и
останутся; конкретные опции подставит поток выбора фреймворка).

| режим | что значит | типичные страницы | `Cache-Control` ответа | индексируется |
|---|---|---|---|---|
| `static` | HTML вычислен заранее (на билде или при первом запросе) и живёт до релиза | лендинг, `/about`, юридическое, посты блога | `no-cache` + `ETag` | да |
| `cached` | HTML собирается на запрос, кладётся в кеш процесса на TTL, обновляется фоном (SWR) | список блога, теги, каталог из API, главная с «последними» | `no-cache` + `ETag` (ответ может быть stale) | да |
| `dynamic` | на каждый запрос, кеш запрещён | `/now`, поиск, preview, персональное | `private, no-store` (или `no-cache` для публичного, но живого) | обычно нет |
| `client` | сервер отдаёт каркас, данные — на клиенте | кабинет, интерактивный калькулятор с приватными данными | `private, no-store` | **никогда** |

Инварианты (гейт в тестах):
- `indexable: yes` ⇒ режим ∈ {`static`, `cached`, `dynamic`} и **весь основной контент —
  в первом HTML-ответе** (канон I-1);
- `guard ≠ public` ⇒ `client`/`dynamic` + `noindex` + `private, no-store` + нет в sitemap
  (канон I-14);
- `client` + `indexable: yes` — запрещённая комбинация (гейт `/scaffold`).

**Почему `Cache-Control: no-cache` на HTML, а не `max-age`**: без CDN `s-maxage`
бесполезен, а `max-age` на своём домене даёт застрявшие у пользователей страницы после
релиза; `no-cache` + `ETag` — это «спроси и получи 304» (решение зафиксировано в
`04-runtime-deploy.md` §3.3, п. 4).

#### 2.2.2. Развилка: абсолютные URL известны только в контейнере

Канон требует **абсолютных** URL в `canonical`, `og:url`, `og:image`, `hreflang`, JSON-LD,
sitemap, RSS. Google дословно: *«Use absolute paths rather than relative paths with the
`rel="canonical"` `link` element»* **[П]**
https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls
(проверено 2026-09-15). OG-скрейперы относительные URL не резолвят (канон 2.2.2).

При этом `SITE_URL` по канону экосистемы — **runtime**-переменная контейнера
(`04` §3.5), а prerender происходит **на билде**. Это и есть развилка. Она не
«теоретическая»: у всех рассмотренных фреймворков конфиг канонического хоста — build-time:

- **Astro**: *«`site` — Your final, deployed URL. Astro uses this full URL to generate your
  sitemap and canonical URLs in your final build»* **[П]**
  https://docs.astro.build/en/reference/configuration-reference/ (2026-09-15);
- **Astro**, добивающее: *«This rendering occurs at build time for all prerendered pages»* —
  middleware для prerender-страниц **не выполняется на запрос** **[П]**
  https://docs.astro.build/en/guides/middleware/ ⇒ «перепишем в middleware» для статики
  не работает;
- **SvelteKit 2**: динамические env недоступны при prerender — *«prerendered pages that
  make use of 'dynamic' environment variables are really 'baking in' build time values,
  which is incorrect»*; при заходе на prerender-страницу SvelteKit запрашивает актуальные
  значения `$env/dynamic/public` отдельным модулем `/_app/env.js` — то есть **на клиенте,
  после загрузки HTML**, что для `<head>` бесполезно **[П~]**
  https://svelte.dev/docs/kit/$env-dynamic-public + issues sveltejs/kit#10008, #10737;
- **Nuxt**: `runtimeConfig` подменяется env'ом на рантайме, но prerender-страницы
  генерируются на билде; у Nuxt SEO для этого отдельный гайд «Runtime Site Config»,
  где site config подменяется **в Nitro-плагине/мидлваре на запрос** — то есть только для
  SSR-ответов **[П~]** https://nuxtseo.com/docs/site-config/guides/runtime-site-config.

#### 2.2.3. Шесть способов это решить — и честная цена каждого

| # | Способ | Один образ на все среды | Цена в рантайме | Новые классы ошибок | Вердикт |
|---|---|---|---|---|---|
| **A** | `SITE_URL` как build ARG, свой образ на среду | ❌ | 0 | «в проде образ, который не тестировали на staging» | только для проектов **с одной средой**; фиксируется строкой в `rendering.md` как осознанный отказ |
| **B** | Prerender при старте контейнера | ✅ | старт 10–60 с, нужен билд-тулчейн в runtime-образе, writable FS | «контейнер не поднялся, потому что упал рендер» | нет |
| **C** | **Плейсхолдер + штамповка при старте**: на билде в HTML пишется `__SITE_ORIGIN__`, entrypoint заменяет его на `$SITE_URL` | ✅ | ~0 (один проход по файлам при старте) | забытый плейсхолдер уедет в выдачу | **да, как оптимизация** |
| **C′** | Prerender **тела**, `<head>` собирается на запрос (шов-маркер в шаблоне) | ✅ | микросекунды на склейку | зависит от шва конкретного фреймворка | как вариант C, если фреймворк даёт шов |
| **D** | **Без prerender: SSR + кеш в процессе** (LRU + SWR, прогрев при старте) | ✅ | первый рендер URL — десятки мс | кеш холодный после релиза | **да, дефолт шаблона** |
| **E** | Относительные `canonical`/`og:url` | ✅ | 0 | Google рекомендует абсолютные, OG-скрейперы относительные не резолвят | **нет** |
| **F** | Origin из запроса (`Host` + `X-Forwarded-Proto`) | ✅ | 0 | host-header poisoning — **снимается тем, что Traefik матчит роутер по `Host(...)`**, чужой Host до приложения не доходит | да, **как дополнение к D** (и как ассерт «Host == SITE_URL») |

Ключевое наблюдение, которое делает всю развилку дешёвой:

> **Абсолютные URL нужны только в `<head>`, JSON-LD, фидах и sitemap. В теле документа
> ссылки должны быть корневыми относительными (`/blog/x`).**

Это правило (а) режет поверхность «штамповки» до десятка строк в `<head>`, (б) страхует
от переезда домена, (в) проверяется одной регуляркой в e2e: в `<body>` нет `https://<origin>`.

**Рекомендация потока:**

1. **Дефолт — D.** Все страницы, кроме заведомо мёртвой статики, рендерятся на запрос и
   кешируются в памяти процесса; `SITE_URL` читается из env на каждом рендере. Никаких
   плейсхолдеров, никакого нового класса ошибок, вебхук-инвалидация возможна.
   TTFB кеш-хита практически равен отдаче статического файла (оба — из RAM).
2. **C — включаемая оптимизация** для «холодных» страниц (лендинг, `/about`, юридическое,
   старые посты) на больших сайтах и при заметном трафике. Механика — 20–30 строк в
   entrypoint + e2e-тест «в ответе нет `__SITE_ORIGIN__`». Прецедентов два:
   - сам SPA-шаблон stit уже так делает — `docker/nginx-entrypoint.sh` генерирует
     `/config.js` из env контейнера **[П]** (чтение репо);
   - готовый инструмент того же класса: `@import-meta-env/cli` **0.7.4**, MIT,
     опубликован 2025-09-22, слоган «Build once, deploy anywhere. Startup/runtime
     environment variable solution for JavaScript» **[П]**
     https://registry.npmjs.org/@import-meta-env%2Fcli (проверено 2026-09-15).
     Брать зависимость не обязательно — паттерн важнее пакета.
3. **A — только с явной записью** в `docs/stack/rendering.md` («у проекта одна среда,
   staging нет») и с пониманием, что `make bump` тега между средами больше не переносим.
4. **E — запрещено** правилом `seo-invariants`.
5. **`robots.txt`, `sitemap*.xml`, `rss.xml`, OG-картинки, `/healthz` — всегда динамические
   server routes**, независимо от режима остальных страниц: они дешёвые и обязаны знать
   runtime-origin и runtime-политику индексации (канон I-9, I-11).

При C обязательное следствие: **HTML не предсжимать на билде** (иначе плейсхолдер внутри
`.br`/`.gz`). Предсжимаются только ассеты (JS/CSS/SVG), HTML жмёт Traefik `compress`
(`encodings: [br, gzip]`, без `defaultEncoding: zstd` — канон P-17).

#### 2.2.4. Требования к фреймворку, вытекающие из развилки (вход для потоков 07–11)

1. Есть **серверный кеш HTML в процессе** или возможность его добавить одним слоем
   (middleware/hook), с ключом «метод + путь + локаль» и **без** cookie/UA в ключе.
   Встроено: Nitro (`routeRules.swr`, драйвер memory) **[П]** `04` §2.7; Next.js (ISR,
   fs-кеш, работает и в Docker/Node без CDN; заголовок `x-nextjs-cache: HIT|STALE|MISS|
   REVALIDATED`; на нескольких инстансах нужен общий cacheHandler) **[П]**
   https://nextjs.org/docs/app/guides/incremental-static-regeneration (версия доки 16.3.5,
   2026-06-23). Не встроено: Astro, SvelteKit — пишется руками (middleware/обёртка сервера).
2. Есть возможность **отключить стриминг** для ботов или целиком (канон P-3): у Astro Node-
   адаптера это опция `experimentalDisableStreaming` **[П]**
   https://docs.astro.build/en/guides/integrations-guide/node/.
3. Можно отдавать произвольные статусы (301/308/404/410/429/503) из кода маршрута.
4. `<head>` формируется из данных, доступных **до** рендера тела (канон P-1).
5. Статика отдаётся самим процессом с `immutable` на хешированных ассетах (у Astro Node-
   адаптера `dist/client/_astro/**` получает `Cache-Control: public, max-age=31536000,
   immutable` автоматически **[П]** там же).

#### 2.2.5. Инвалидация без CDN — четыре механизма, ни одного лишнего

| механизм | для чего | как устроен |
|---|---|---|
| **релиз** | git-контент, шаблоны, стили | новый образ = пустой кеш = атомарная публикация; отката нет отдельного — это `make bump` со старым тегом |
| **TTL + SWR** | контент из API/CMS | `cached`-режим: `maxAge` (свежо) + `staleMaxAge` (отдаём старое, обновляем фоном) |
| **вебхук** | публикация в CMS | `POST /internal/revalidate` с HMAC-подписью тела и `{"paths":[…]}` / `{"tags":[…]}`; отвечает 202; неизвестный путь — 204, не 500 |
| **ручной flush** | инцидент | `POST /internal/cache/flush` (тот же секрет) + ответ со счётчиком сброшенных ключей |

Инварианты: оба `/internal/*` — **не в sitemap, `noindex`, rate-limit, только POST,
константное сравнение подписи**; ключ кеша не содержит cookie/UA/query вне whitelist;
ответ несёт `X-Cache: HIT|STALE|MISS|BYPASS` (конвенция Nitro/Next — пригодится в smoke).
Прогрев после релиза — список «горячих» URL (из `rendering.md`) дёргается при старте
в фоне, не блокируя `/healthz`. **[?]** (инженерное решение; собрано из практик Next/Nitro)

#### 2.2.6. Как контент попадает в HTML (ключевое требование к пайплайну)

> **Markdown компилируется на билде. На запрос собирается только страница.**

Иначе `cached`/`static` через SSR обойдётся дорого: парсинг MD + подсветка кода — это
десятки-сотни миллисекунд на документ. Поэтому контент-слой обязан давать:

- `content-index.json` (или SQLite) — frontmatter всех документов + пути + теги + даты
  (для списков, sitemap, RSS, поиска, hreflang);
- скомпилированный HTML тела каждого документа (или его AST) — рядом, лениво читаемый;
- всё это валидируется Zod-схемой на билде, ошибка схемы = красная сборка.

Такой индекс делает `cached`-режим дешёвым (склейка строк), а `static` — вырожденным
случаем «кеш, прогретый заранее».

### 2.3. Изображения

#### 2.3.1. Два пайплайна, между ними — граница источника

| | контент в git | контент извне (CMS/API/пользователь) |
|---|---|---|
| когда обрабатываем | на билде | на запрос, с дисковым кешем |
| что получаем | `AVIF` + `WebP` + фолбэк, ширины `400/800/1200/1600`, контент-хеш в имени | то же, но по требованию и по белому списку ширин |
| заголовки | `public, max-age=31536000, immutable` | `immutable` по контент-хешу; «логический» URL — короткий `max-age` + `ETag` |
| цена | время сборки (+секунды на десяток картинок), размер образа | CPU первого запроса, диск под кеш |
| риск | образ пухнет, если оригиналы в репо большие | SSRF/усиление, если нет allowlist |

**Правило шва**: URL картинки контента строится одной функцией `picture(src, {sizes, priority})`,
которая сама решает, это build-ассет или `/img/...`. Страницы не знают про пайплайн.

#### 2.3.2. Разметка (канон P-9/P-10)

```html
<!-- LCP-герой: без lazy, с приоритетом, с фолбэком src -->
<picture>
  <source type="image/avif" srcset="/a/hero-800.avif 800w, /a/hero-1600.avif 1600w" sizes="100vw">
  <source type="image/webp" srcset="/a/hero-800.webp 800w, /a/hero-1600.webp 1600w" sizes="100vw">
  <img src="/a/hero-1600.jpg" width="1600" height="900" alt="…" fetchpriority="high" decoding="async">
</picture>
```

- Google индексирует **только `<img src>`** (CSS-фоны — нет) и требует фолбэк-`src`
  при `srcset`/`<picture>` (канон 2.7) — поэтому `<picture>` всегда с `<img src>`.
- `width`/`height` обязательны (CLS), `loading="lazy"` — всем, кроме LCP.
- Декоративное — `alt=""`; содержательное — описательный `alt` (он же попадает в
  Google Images).

#### 2.3.3. Хранение оригиналов

- **В репо** (`content/assets/**`) — пока суммарно ≲ 50 МБ: контент и его картинки
  версионируются и ревьюятся вместе, откат работает целиком.
- **MinIO из инфра-шаблона** (`s3.${DOMAIN}`) — когда картинки загружает редактор/
  пользователь либо объём переваливает за сотню мегабайт: тогда в контенте живёт ссылка,
  а рантайм-ресайз ходит в MinIO по внутренней сети.
- Git-LFS — **не рекомендую**: добавляет требование к клиенту и к Gitea, а выигрыш для
  десятков мегабайт не окупается. **[?]**

#### 2.3.4. OG-картинки

- Стратегия по умолчанию: **картинка из контента**, если задана; иначе — **генерация**
  `/og/<key>.png` из шаблона (заголовок + бренд), ключ = хеш(title + версия шаблона),
  дисковый кеш, `immutable`; иначе — статический `/og/default.png`.
- Размер один: **1200×630 PNG/JPEG** (канон 2.2.2), абсолютный HTTPS-URL,
  `og:image:width/height/alt` всегда, вес < 1 МБ (наш бюджет — 300 КБ).
- Заголовок **запекать в картинку** (X исторически менял поведение подписи).
- Генератор: связка «layout HTML/CSS → SVG → PNG» (satori + resvg) — по канону 2.2.3
  единственная, что работает на alpine/musl без системных шрифтов; кириллический
  TTF/OTF кладётся в образ (satori не читает WOFF2).

#### 2.3.5. LCP-политика

1. LCP-элемент контентной страницы — либо заголовок (тогда картинок выше сгиба нет и
   LCP = текст, что лучше всего), либо одна герой-картинка.
2. Герой: AVIF ≤ 150 КБ, `fetchpriority="high"`, без `lazy`, размеры заданы,
   `preload` — **только если измерение показывает выигрыш** (он конкурирует со шрифтом).
3. Никаких слайдеров/каруселей в первом экране — это LCP-убийца и лишний JS.
4. Картинки в теле поста — `lazy` + `decoding="async"`.

### 2.4. Шрифты

#### 2.4.1. Политика (канон P-7/P-8)

| правило | почему |
|---|---|
| **self-host**, только `WOFF2` | приватность, отсутствие лишнего connect, WOFF2 сжимает на ~30 % лучше WOFF |
| **variable**-начертание, 1 файл на сабсет | вместо 4–6 статических |
| **сабсеты по `unicode-range`**: `latin` и `cyrillic` раздельно | англоязычная страница не тянет кириллицу и наоборот |
| `font-display: swap` для брендовых заголовков, `optional` — для основного текста | `optional` даёт минимальный CLS |
| **preload ≤ 1 файла**, выбранного по активной локали, с `crossorigin` | preload игнорирует `unicode-range` — прелоадить оба сабсета значит качать лишнее |
| метрики фолбэка (`size-adjust`, `ascent-override`, `descent-override`) | убирает скачок при подмене шрифта |
| максимум **2 семейства** (текст + акциденция), лучше одно | каждое семейство — это ещё 2 сабсета и ещё один рендер-барьер |

#### 2.4.2. Открытые шрифты с полной кириллицей

Требование из §2.4.1: не Inter (перегрет), OFL/Apache, variable, кириллица не «в
довесок», есть готовый self-host-пакет. Проверялись пакеты `@fontsource-variable/*`
(**версия 5.3.0 от 2026-07-19** у всех, кроме Onest — 5.3.1 от 2026-08-30; лицензия у

##### Главный вывод, который меняет выбор: курсив

Самые «кириллица-первые» семейства (**Manrope, Golos Text, Onest, Geologica, Unbounded,
Ruda, Wix Madefor Display**) в поставке Fontsource **не имеют italic вовсе** — в
`metadata.json` у них `styles: ["normal"]` [П]. Для контент-сайта это не мелочь: в теле
статьи есть `<em>`, названия, цитаты; браузер нарисует **синтетический наклон**, и это
видно. Поэтому текстовый шрифт выбирается **сначала по наличию курсива**, а потом по
весу и характеру.

##### Рекомендация дефолта шаблона

- **Основной текст — `Wix Madefor Text Variable`**: настоящий курсив, `wght 400–800`
  (ровно диапазон, нужный контентному сайту: без бесполезных 100–300), кириллица 13,8 КБ —
  один из самых лёгких вариантов *с курсивом*, и семейство не заезжено в RU-вебе.
- **Акциденция (заголовки, hero) — опционально `Onest Variable`** (15,5 КБ, кириллица
  родная) либо **`Golos Text Variable`**, если заказчику нужен выраженно «русский»
  характер. Суммарно два сабсета ≈ **29–35 КБ** — вдвое ниже бюджета §2.11.2 (60 КБ).
- **Однофайловый вариант** (когда «максимально просто»): `Rubik` или `Source Sans 3` —
  одно семейство, курсив есть, 14,8/18,1 КБ.
- **Никогда по умолчанию**: `Roboto Flex` (легко утащить 132 КБ), `Commissioner` в
  `full`-сборке, `Noto Sans` `cyrillic-ext`, статический `PT Sans`.

##### Как это конфигурируется в Astro (Fonts API — стабилен)

Fonts API в текущем Astro — **не экспериментальный**, верхнеуровневая опция `fonts`,
провайдеры `fontProviders.fontsource()` / `.google()` / `.local()`; файлы скачиваются на
билде и отдаются с самого сайта из `_astro/fonts` [П]
https://docs.astro.build/en/guides/fonts/, https://docs.astro.build/en/reference/configuration-reference/.

**Три дефолта, которые обязаны быть переопределены** [П]:
`subsets` по умолчанию `["latin"]` (кириллицы не будет вовсе!), `weights` — `[400]`
(вариативный диапазон задаётся строкой, например `["400 800"]`), `styles` — `["normal","italic"]`
(для семейств без курсива это лишний запрос файла).

```js
// astro.config.mjs — черновик
import { defineConfig, fontProviders } from 'astro/config'

export default defineConfig({
  fonts: [
    {
      provider: fontProviders.fontsource(),
      name: 'Wix Madefor Text',
      cssVariable: '--font-text',
      weights: ['400 800'],            // весь variable-диапазон одним файлом
      styles: ['normal', 'italic'],
      subsets: ['cyrillic', 'latin'],  // ДЕФОЛТ — только latin
      display: 'optional',             // основной текст: минимальный CLS (§2.4.1)
      fallbacks: ['system-ui', 'sans-serif'],
      optimizedFallbacks: true,        // метрики фолбэка считает Astro
    },
    {
      provider: fontProviders.fontsource(),
      name: 'Onest',
      cssVariable: '--font-display',
      weights: ['600 800'],
      styles: ['normal'],              // у Onest курсива нет — не просить
      subsets: ['cyrillic', 'latin'],
      display: 'swap',                 // акциденция: swap
      fallbacks: ['system-ui', 'sans-serif'],
    },
  ],
})
```

```astro
---
// src/app/... корневой layout — черновик
import { Font } from 'astro:assets'
---
<Font cssVariable="--font-text" preload />   <!-- ровно один preload (§2.4.1) -->
<Font cssVariable="--font-display" />
```

⚠️ Инвариант C-22 (`preload ≤ 1 файла активной локали`) при двух сабсетах на семейство
требует внимания: `preload` игнорирует `unicode-range`, поэтому прелоадится **только**
файл текстового шрифта нужной локали. Если фреймворк не даёт выбрать конкретный файл —
не прелоадить ничего, это дешевле, чем качать латиницу на русской странице. **[?]**

⚠️ Альтернатива провайдеру `fontsource` — `local` с файлами, положенными в репо: снимает
зависимость сборки от сети (npm-реестр во время `docker build`) и даёт возможность
**самостоятельно сабсетить** шрифт под реально используемые глифы. Для шаблона дефолт —
`fontsource` (воспроизводимо, версия в lock-файле), для проектов с брендовым шрифтом —
`local`. **[?]**

### 2.5. Поиск по сайту

#### 2.5.1. Развилка по объёму и источнику

| вариант | объём | где считается | цена | когда |
|---|---|---|---|---|
| **статический индекс** (индексируется собранный контент, поиск — в браузере, индекс качается кусками) | до ~5–10 тыс. документов | на билде | +шаг сборки, +индекс в образе, JS только на `/search` | дефолт для блога/доков/корпоративного |
| **клиентский индекс целиком** (один JSON в память браузера) | до ~500 документов | на билде | индекс качается целиком — следить за весом | маленький сайт, где нужен мгновенный фильтр |
| **серверный поиск** (SQLite FTS5 / Postgres `tsvector` на бэкенде) | без ограничений | на сервере | +эндпоинт, +индексация при публикации | каталог с фасетами, контент из CMS/API |
| нет поиска | — | — | 0 | лендинг на 5 страниц — поиск вреден (пустая страница-результат в индексе) |

#### 2.5.2. Инварианты

- Страница `/search` — **`noindex, follow`**, вне sitemap (иначе фабрика soft-404).
- Поиск работает **без JS в деградации**: форма `GET /search?q=` уходит на сервер, сервер
  отдаёт результаты HTML'ом (для статического индекса — хотя бы список разделов и
  подсказку). Полностью JS-only поиск на контентном сайте допустим, но тогда `/search`
  должен честно отдавать 200 с пустым состоянием и не притворяться контентом.
- **i18n**: индекс на локаль; выбор индекса — из `lang` страницы.
- **Русская морфология** — обязательный критерий выбора движка: без стемминга поиск по
  русскому тексту находит только точные формы.
- Если часть страниц рендерится на запрос (`cached`/`dynamic`), индекс строится **из
  контент-индекса**, а не краулингом собранных файлов — иначе половина сайта в поиск не
  попадёт.

### 2.6. Формы и антиспам

#### 2.6.1. Базовая механика — прогрессивное улучшение

```
<form method="post" action="/api/contact">   ← работает без JS
   ↓ POST (application/x-www-form-urlencoded)
сервер: origin-check → honeypot → time-trap → rate-limit → [капча] → валидация (Zod)
   ↓ успех                                   ↓ ошибка
303 → /contacts/spasibo                      200 + та же форма с текстом ошибки
                                              (aria-live, поля сохранены)
```

- **Post/Redirect/Get** обязателен: без него F5 повторяет отправку, а «спасибо» не
  адресуемо (аналитике нечего считать).
- Островок-скрипт только улучшает: инлайн-валидация, блокировка двойного сабмита,
  отправка `fetch` без перезагрузки. Отключённый JS ничего не ломает.
- Успех — **отдельный URL** `/contacts/spasibo` с `noindex`.

#### 2.6.2. Антиспам-лестница (от дешёвого к дорогому)

| ступень | что | стоимость для пользователя | эффективность |
|---|---|---|---|
| 1. honeypot | скрытое поле, заполненное ботом → 204 «ок» без отправки | 0 | режет примитивные боты |
| 2. time-trap | подписанная метка времени в форме; отправка быстрее ~3 с или позже ~2 ч — отказ | 0 | режет автоматические сабмиты |
| 3. origin-check | `Sec-Fetch-Site: same-origin` либо `Origin` == `SITE_URL` | 0 | режет кросс-сайтовые сабмиты |
| 4. rate-limit | по IP: N/мин в приложении + отдельный Traefik-роутер на путь формы | 0 | режет флуд |
| 5. капча | внешний сервис | заметная | режет целевой спам |

OWASP по (3): проверка `Origin`/`Referer` и Fetch Metadata — **защита в глубину**, не
самостоятельная мера; заголовки иногда отсутствуют, поэтому правило формулируется как
«совпало ИЛИ отсутствует», а не «обязано совпасть» **[П]**
https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html.
Для анонимной публичной формы токен-CSRF не обязателен (нет сессии, которую можно
использовать), но подписанная метка времени из (2) заодно играет роль такого токена.

**Капча включается шовно**: `CAPTCHA_PROVIDER=none|smartcaptcha|turnstile|hcaptcha` +
серверная верификация в одном месте. Дефолт шаблона — `none` (ступени 1–4), потому что
любая внешняя капча — это внешняя зависимость и риск недоступности части аудитории.
Доступность провайдеров в РФ — §2.7.4.

#### 2.6.3. Доставка заявки

| канал | когда | что важно |
|---|---|---|
| **Telegram-бот** | у заказчика нет почтовой инфраструктуры (частый случай) | токен — только на сервере; лимиты Bot API; ретрай с backoff; не терять заявку при ошибке (лог + очередь в памяти) |
| **SMTP-relay** | есть корпоративная почта | SPF/DKIM/DMARC домена, иначе письма в спам; таймаут и ретрай |
| **бэкенд экосистемы** | заявка — доменная сущность (лид, запись) | обычный API-вызов по внутренней сети, вся логика и хранение — там |

Никогда: отправка с клиента напрямую в Telegram/почтовый сервис (утечка токена),
хранение заявок в браузере, логирование тела заявки (ПДн).

#### 2.6.4. Юридический минимум формы (РФ)

- Чекбокс согласия на обработку ПДн (не предустановленный) + ссылка на политику.
- Страница политики обработки ПДн — обязательный reference-слайс (`/legal/privacy`).
- В логах — факт отправки и идентификатор, **не** содержимое.
- Хранение: если заявки складываются в БД — это обработка ПДн со всеми вытекающими
  (§2.7.3).

#### 2.6.5. Доставка заявки: Telegram Bot API и SMTP

##### Telegram Bot API — лимиты

Актуальная версия — **Bot API 10.3 (24.08.2026)** [П] (чтение `core.telegram.org/bots/api`,
раздел Recent changes). Официальные лимиты [П] https://core.telegram.org/bots/faq:

- «In a single chat, avoid sending **more than one message per second**»;
- «In a group, bots are not be able to send **more than 20 messages per minute**»;
- «For bulk notifications, bots are not able to broadcast **more than about 30 messages
  per second**, unless they enable paid broadcasts» (платный режим — до 1000/с через
  `@BotFather`);
- при превышении приходит **429**, и в теле — `parameters.retry_after`: «In case of
  exceeding flood control, the number of seconds left to wait before the request can be
  repeated» [П] (`ResponseParameters` в Bot API).

Для формы обратной связи это лимиты с колоссальным запасом: проблема не в них.

##### Доступность Telegram в РФ в 2026 — вот где проблема

Факты по первоисточникам:

- **август 2025** — РКН заблокировал звонки в Telegram и WhatsApp (мера против
  телефонного мошенничества) [П~];
- **10.02.2026** — РКН публично подтвердил, что **продолжит последовательно ограничивать
  работу Telegram**; дословно: «К сожалению, рядом мессенджеров, в том числе Telegram,
  эти нарушения не устранены. По-прежнему не исполняется российское законодательство, не
  защищены персональные данные, нет реальных мер противодействия мошенничеству и
  использованию мессенджера в преступных и террористических целях» [П]
  https://www.interfax.ru/digital/1072012 (та же новость — `tass.ru/obschestvo/26403011`,
  `kommersant.ru/doc/8420604`). Ограничения описаны как **поэтапные**: замедление,
  проблемы с загрузкой медиа (кружки, голосовые, сторис, фото, видео), ранее — звонки.
  Условие снятия — исполнение законодательства и размещение серверов в РФ [П~];
- в течение 2026 сообщается о нарастании ограничений вплоть до «мессенджер формально
  работает, но пользоваться им полноценно трудно» [П~].

**Измерено 2026-09-16 с этой машины [изм]:** `api.telegram.org` **доступен** —
`https://api.telegram.org/bot<фиктивный токен>/getMe` отдаёт
`{"ok":false,"error_code":401,"description":"Unauthorized"}` по HTTP/2 с заголовком HSTS;
`core.telegram.org` — 200. То есть **серверная отправка с VPS сегодня работает**.

**Как это правильно понимать.** Риск здесь не «сервер не сможет отправить», а
**«получатель не сможет прочитать»**: заявка уходит менеджеру, который открывает Telegram
на российском мобильном интернете. Технически доставленная и фактически не увиденная
заявка — хуже, чем неотправленная, потому что её никто не ищет. Плюс второй риск:
доступность `api.telegram.org` с конкретного VPS зависит от провайдера и может измениться
без предупреждения.

⇒ **Telegram не может быть единственным каналом доставки заявок в РФ-проекте на
2026-09-16.** Он допустим как *дублирующий* или как «быстрый пинг», но не как система
учёта лидов.

##### SMTP-релей — бесплатного больше нет

Подтверждение лида из `ROUND2-CONTEXT.md`:

- **Mail.ru — с 12.06.2026**: доступ к ящикам `@mail.ru` по IMAP/POP3/**SMTP** из
  сторонних приложений остался только в платной подписке **Mail Space** (от 199 ₽/мес)
  [П~];
- **Яндекс — с 29.06.2026**: работа с Яндекс Почтой по IMAP/SMTP/POP3 недоступна без
  тарифа **Яндекс 360** (от ~166 ₽/мес при годовой оплате) [П~]
  (Habr `1042832`, CNews, linux.org.ru; собственные страницы помощи Яндекса этот переход
  уже не описывают — там остались только лимиты).

То есть **CRM, сайты и скрипты, ходившие через бесплатный SMTP, сломались в июне 2026** —
и это ровно наш случай «форма шлёт письмо».

Действующие лимиты отправки Яндекса (официальная справка) [П]
https://yandex.ru/support/yandex-360/customers/mail/ru/web/letter/create/send-many-letters:
**через SMTP — до 300 писем в сутки**, через веб — 1000, через мобильное приложение — 50;
письмо на 10 адресатов считается за 10 писем; при «массовой рассылке шаблонных или
однотипных писем» блокировка наступает раньше.

Обязательная DNS-обвязка: **SPF + DKIM + DMARC** на домене отправителя — у Яндекс 360
значение DKIM берётся из админки и «его нужно внести обязательно, иначе письма могут
начать возвращаться с ошибкой» [П~]
https://yandex.ru/support/yandex-360/business/admin/ru/domains/dns/dkim. Без этого письма
с формы уезжают в спам, и заказчик узнаёт об этом через месяц по отсутствию заявок.

| вариант | плюс | минус |
|---|---|---|
| **Яндекс 360 для бизнеса / Mail Space** (ящик на домене заказчика) | почта уже есть у бизнеса, SPF/DKIM настраиваются один раз, письма приходят туда, куда смотрит менеджер | платно; 300 писем/сутки; нужен пароль приложения |

| **свой Postfix на VPS** | ноль внешних зависимостей | репутация IP VPS, PTR, прогрев, попадание в блок-листы — **не рекомендую для заявок** **[?]** |

##### Рекомендация: шов `FORM_DELIVERY` и «не потерять заявку»

```
FORM_DELIVERY=backend            # дефолт, когда у проекта есть go-backend экосистемы
FORM_DELIVERY=smtp               # дефолт для сайта без бэкенда
FORM_DELIVERY=smtp,telegram      # список: доставка во все каналы, успех = хотя бы один
```

Контракт (черновик, инженерное решение — **[?]**):

```ts
// src/shared/forms/delivery.ts
export interface DeliveryChannel {
  readonly id: 'telegram' | 'smtp' | 'backend'
  send(lead: Lead): Promise<void>      // бросает при неуспехе
}
```

Поведение, зашитое в шаблон:

1. **Сначала запись, потом доставка.** Заявка сериализуется в **durable-очередь на диске**
   (`LEADS_SPOOL_DIR`, по файлу на заявку, имя = ULID) **до** первой попытки отправки.
   Ответ пользователю (303 → `/contacts/spasibo`) даётся после успешной записи в спул, а
   не после доставки: пользователь не должен ждать Telegram. Это прямо противоречит
   соблазну «отправить и забыть» и является главным требованием раздела.
2. **Доставка — фоном, с ретраями и джиттером**: 5 попыток, backoff 1с → 5с → 30с → 5м →
   30м; для Telegram при 429 — пауза ровно `parameters.retry_after` (+1 с), не
   экспоненциальный backoff.
3. **Успех = хотя бы один канал.** Файл из спула удаляется, когда подтверждён хотя бы
   один канал; остальные каналы дописывают статус в тот же файл.
4. **Спул переживает рестарт контейнера** ⇒ это именованный volume, а не `tmpfs`
   (взаимодействует с T-5 из §5.2: `read_only: true` + отдельный volume под `/var/spool/leads`).
5. **Наблюдаемость**: счётчик «в спуле сейчас N» в `/healthz`-соседе (`/metrics` или лог
   при старте), и **алерт, если N > 0 дольше 15 минут** — иначе тихо накопится сотня
   заявок. Отправка алерта — по тому же каналу, что и заявки, плюс Sentry.
6. **В спуле лежат ПДн** ⇒ каталог не в образе, не в бэкапе «как есть» без согласования,
   ретенция ограничена (`LEADS_SPOOL_TTL_DAYS`, дефолт 30), содержимое не логируется (§2.7.3).
7. **Гейт (e2e)**: (а) при недоступном канале форма всё равно возвращает 303 и заявка
   появляется в спуле; (б) после «поднятия» канала спул опустошается; (в) тело заявки не
   встречается в логах.

### 2.7. Аналитика и согласия

#### 2.7.1. Что ставим по умолчанию

Для русскоязычного заказчика базовый набор — **Яндекс.Метрика** (она же даёт «обход по
счётчику» в Вебмастере — ускорение обнаружения новых URL, канон 2.6) и, по запросу,
GA4. Оба — «третьи стороны» со всеми последствиями для INP.

Правила подключения (канон P-14):

1. Счётчик **не грузится**, пока нет согласия (если проект решил, что согласие нужно —
   §2.7.3).
2. Загрузка — после гидрации островка или по `requestIdleCallback`/первому
   взаимодействию; никогда не синхронно в `<head>`.
3. Вклад в INP/TBT измеряется: LHCI с бюджетом на скрипты третьих сторон + RUM.
4. Никаких ПДн в URL (канон приватности) и в параметрах события.

#### 2.7.2. Альтернатива без третьих сторон

Self-hosted аналитика (Plausible CE / Umami / Matomo) ставится тем же способом, что и
CMS, — **это ещё один контейнер и ещё одна БД на том же VPS**. Разумно, когда:
(а) заказчику принципиально «данные у нас», (б) хватает базовой статистики,
(в) кто-то будет это обновлять. Иначе — Метрика.

Дешёвый промежуточный вариант: **серверная статистика из access-log Traefik** (страницы,
коды, боты) — ноль скриптов на клиенте, ноль согласий; не даёт поведения и конверсий.

##### Нужен ли cookie-баннер по российскому праву

**Прямой нормы «сайт обязан показать cookie-баннер» в российском праве нет** — аналога
ePrivacy Directive не существует, и первоисточника уровня закона/приказа РКН, который бы
такое требовал, найти не удалось [П] (искал по rkn.gov.ru, consultant.ru, publication.pravo.gov.ru).
Требование выводится косвенно и в два шага:

1. cookie/идентификатор устройства/IP **в совокупности** могут позволять определить
   физлицо ⇒ являются ПДн (позиция РКН, воспроизводимая в разъяснениях и практике) **[П~]**
   — единственную формулировку на официальном домене РКН найти не удалось, все доступные
   изложения — вторичные;
2. если это ПДн, то нужна законное основание (ст. 6) ⇒ для аналитических/маркетинговых
   cookie основание — согласие (ст. 9) ⇒ на практике это баннер + политика.

Отсюда — честная формулировка для `docs/stack/seo.md`: **баннер не обязателен законом,
но является стандартным способом получить согласие там, где оно требуется; для
строго-технических cookie (сессия, CSRF, выбор темы/локали) согласие не нужно**, и их
нельзя мешать в один чекбокс с аналитикой. **[?]** (инженерный вывод из норм выше)

##### Практический минимум для reference-слайса формы

Дополняет §2.6.4 и превращает его в проверяемый список:

1. **Чекбокс согласия** — обязательный, `required`, **не предустановленный**, отдельным
   полем; подпись: «Я согласен(на) на обработку персональных данных на условиях
   <a href="/legal/privacy">Политики обработки персональных данных</a>». Без галки форма
   не отправляется **и на сервере тоже** (Zod: `consent: z.literal(true)`) — иначе
   валидация обходится curl'ом, а значит обработка идёт без согласия (ч. 2).
2. **Цель одна на одну галку.** Заявка — одна галка; «хочу получать рассылку» — вторая,
   необязательная. Одна галка «на всё» ломает признак «конкретное и предметное» (ст. 9 ч. 1).
3. **Фиксация факта согласия**: вместе с заявкой сохраняются `consent_version` (хеш/дата
   версии текста политики), `consented_at`, способ (форма/страница). Текст политики
   версионируется в git — это и есть доказательство. **[?]**
4. **Страница `/legal/privacy`** — `static`, индексируется, есть в sitemap, ссылка в
   футере на каждой странице (О-1 требует именно «на страницах, используемых для сбора»).
5. **В логах — только факт и идентификатор**, никогда тело заявки (само логирование
   содержимого — это ещё одно место обработки ПДн, которое надо описывать и защищать).
6. **Хранение — в РФ.** Заявка уходит в БД проекта/бэкенд экосистемы на том же VPS; если
   канал доставки внешний (§2.6.5), это фиксируется в политике как передача третьему лицу.
7. **`/de-template`** обязан заменить в политике плейсхолдеры оператора (название, ИНН,
   адрес, e-mail ответственного) и **упасть**, если они остались — иначе демо-политика
   уедет в прод (добавить к инварианту C-24).
8. **Cookie-баннер** — островок, поставляется с двумя категориями («технические» —
   всегда, «аналитика» — по согласию), решение об использовании принимает владелец сайта
   (риск R-6). Счётчики физически не грузятся до согласия (C-17).

#### 2.7.4. Капча и антибот в РФ

Напоминание из §2.6.2: дефолт шаблона — **`CAPTCHA_PROVIDER=none`**, ступени 1–4
(honeypot → time-trap → origin-check → rate-limit) закрывают подавляющую часть спама и
стоят 0 КБ клиентского JS. Капча — пятая ступень, включается только когда первые четыре
доказанно не справились.

##### Шов `CAPTCHA_PROVIDER`

```ts
// src/shared/antispam/captcha.ts — черновик; одна точка верификации на весь сайт
export type CaptchaProvider = 'none' | 'smartcaptcha' | 'turnstile' | 'hcaptcha'

export interface CaptchaVerifier {
  readonly provider: CaptchaProvider
  /** true = пропустить, false = отказать. Никогда не бросает. */
  verify(token: string | null, ip?: string): Promise<boolean>
  /** что положить в <head>/острова; для 'none' — ничего */
  clientScript(): { src: string; siteKey: string } | null
}
```

Правила шва (инварианты, проверяемые тестом):

1. **Ключи.** `CAPTCHA_SITE_KEY` — публичный, может попасть в HTML; `CAPTCHA_SECRET` —
   только `process.env` сервера, в публичный whitelist `config.md` не входит.
2. **Провайдер не должен ронять форму.** Яндекс прямо рекомендует при не-200 от валидации
   «обрабатывать как `"status":"ok"`» [П] — то есть **fail-open**. Это правильный дефолт
   для формы обратной связи (лучше лишний спам, чем потерянная заявка), но он обязан быть
   **явным**: `CAPTCHA_FAIL_MODE=open|closed`, дефолт `open`, и запись в лог каждого
   fail-open. **[?]**
3. **Капча не отменяет ступени 1–4.** Она добавляется к ним, а не заменяет: honeypot и
   time-trap работают и при отключённом JS, капча — нет.
4. **Форма обязана работать без JS.** При `CAPTCHA_PROVIDER != none` форма без JS
   отправится без токена ⇒ сервер должен уметь ответить понятным сообщением и/или
   применить более жёсткий rate-limit, а не молча отклонить. **[?]**
5. **Юридика.** Любая внешняя капча получает IP и поведенческие сигналы посетителя.
   SmartCaptcha прямо требует уведомить пользователей об обработке данных и по умолчанию
   рисует блок-«щит» со ссылкой на документ [П] — его нельзя скрывать, не заменив
   уведомление другим способом. Turnstile/hCaptcha/reCAPTCHA — ещё и трансграничная
   передача (§2.7.3).
6. **Бюджет.** Любая капча пробивает бюджет «30 КБ JS на острова» (§2.11.2) — кроме
   Turnstile (28 КБ), который занимает его целиком. Поэтому капча грузится **только на
   странице с формой** и **только при фокусе на форме/первом вводе**, отдельной строкой
   в `size-limit`. **[?]**

**Смысл цифры 95,8 КБ**: бюджет шаблона на JS контентной страницы — **0 КБ, потолок
30 КБ** (§2.11.2). Один счётчик Метрики — это **три потолка**. Из этого следует не

**отдельная строка в бюджете «третьи стороны»**, не смешанная с бюджетом островов.

заказчиком.

##### Доступность GA4 из РФ — измерение, а не мнение

С этой машины:

- `www.googletagmanager.com` и `www.google-analytics.com` — **TLS-сессия не
  устанавливается**: после `Client hello` приходит `TLS alert, decode error` и
  `unexpected eof while reading` (curl exit 35), одинаково по IPv4 и IPv6, на 443 и на
  80, и при подстановке другого IP через `--resolve`. [изм]
- при этом `www.google.com` (200), `www.gstatic.com` (204), `analytics.google.com` (301)
  и `api.telegram.org` (401) отвечают нормально. [изм]

Картина «рвётся именно на этих SNI, а соседние домены того же владельца живы» —
характерна для селективной фильтрации на стороне сети, а не для сбоя маршрутизации.
Одна точка наблюдения — не доказательство для всей страны, поэтому это **[изм] + [?]**,
и перед решением стоит перепроверить с VPS заказчика. Контекст: медиа сообщают о
продолжающихся ограничениях сервисов Google в РФ [П~] (`rbc.ru`, `fontanka.ru`, 02.2026).

**Следствие для шаблона:** GA4 нельзя закладывать как работающий по умолчанию компонент
для РФ-аудитории. Если заказчику он нужен (зарубежный трафик, требования агентства) —
это `ANALYTICS=metrika|ga4|both|none` с честной записью в `docs/stack/observability.md`
о том, что ga4-ветка может не собирать данные внутри РФ.

### 2.8. Структурированные данные и метаданные **как данные**

#### 2.8.1. Три уровня, три места хранения

| уровень | что | где живёт | как попадает в HTML |
|---|---|---|---|
| **идентичность сайта** | `Organization` (или `LocalBusiness`), `WebSite`, бренд, лого, соцпрофили (`sameAs`), контакты, адрес, часы работы | `docs/stack/seo.md` → генерится в `shared/seo/identity.ts` (типизированный объект + Zod) | `Organization` — на всех страницах (корневой layout), `WebSite` — **только на корне домена** (канон S-1) |
| **страница** | `title`, `description`, `og:image`, `type`, `noindex`, `Article`/`Product`/`Event` | frontmatter контент-документа или запись CMS | `head()` страницы из данных загрузчика (канон P-1: до первого байта) |
| **структура** | `BreadcrumbList` | **выводится из иерархии маршрута**, не пишется руками | widget `breadcrumbs` отдаёт и видимые крошки, и JSON-LD из одного массива |

Правило единого источника: видимые хлебные крошки и `BreadcrumbList` собираются **из
одного и того же массива** — иначе нарушается политика Google «Don't mark up content that
is not visible to readers of the page» (канон S-4).

#### 2.8.2. Что генерировать по умолчанию, а что — никогда

- **По умолчанию**: `Organization` (или `LocalBusiness` для компании с адресом),
  `WebSite` на корне, `BreadcrumbList` на вложенных, `Article` на постах.
- **По требованию**: `Product`/`Offer` (каталог), `Event`, `JobPosting`, `VideoObject`
  (для Яндекса — без разметки видео не индексируется в видеопоиске, канон 2.6),
  `FAQPage` (**только** если заказчик хочет семантику: rich results отключены 07.05.2026),
  `HowTo` (мертво с 2023), `SearchAction`/sitelinks searchbox (снят 21.11.2024) — канон 2.3.1.
- **Никогда**: `meta keywords`, разметка того, чего нет на странице, `AggregateRating`
  без реальных отзывов на странице.

#### 2.8.3. Мета из контента: одна функция, один тест

```ts
// shared/seo/meta.ts — черновик; вход — документ контента, выход — то, что печатает <head>
export function metaFromDoc(cfg: SeoConfig, doc: ContentDoc, ctx: { path: string; locale: Locale }) {
  const url = absolute(cfg.SITE_URL, ctx.path)          // единственная точка, где появляется origin
  return {
    title: doc.seoTitle ?? doc.title,                    // frontmatter может переопределить SERP-заголовок
    description: doc.description,                        // обязателен: гейт схемы коллекции
    canonical: url,
    robots: cfg.INDEXABLE && doc.draft !== true ? 'index, follow' : 'noindex, nofollow',
    og: { type: doc.type === 'article' ? 'article' : 'website', url,
          image: absolute(cfg.SITE_URL, doc.cover?.og ?? '/og/default.png'), locale: ogLocale(ctx.locale) },
    alternates: hreflangFor(doc.translations, ctx),       // только реально существующие переводы
    jsonLd: [organization(cfg), ...(doc.type === 'article' ? [article(cfg, doc, url)] : []),
             breadcrumbs(ctx.path)],
  }
}
```

Инварианты (unit-тесты `shared/seo/*.test.ts`, канон Q-2): `description` непустой и
уникальный; `title` собран по шаблону из `seo.md`; `canonical` абсолютный, без query и
хвостового слеша; директивы robots **не смешивают разрешающие и запрещающие** (Яндекс
выберет разрешающую — канон I-17); `og:image` абсолютный; JSON-LD сериализуется без
`undefined` и валидируется Zod-схемой типа.

### 2.9. i18n контента

#### 2.9.1. Три способа разложить переводы

| способ | как выглядит | плюсы | минусы |
|---|---|---|---|
| **параллельные каталоги** | `content/ru/blog/post.md` + `content/en/blog/post.md` | видно, что переведено, а что нет; редактор понимает без объяснений; легко отдать переводчику папку | связь «это перевод того» держится на соглашении об имени файла |
| frontmatter-поля | один файл, `title.ru` / `title.en` / `body.ru` | всё рядом | тело поста в YAML — нечитаемо; ломается диффом; MD-инструменты не работают |
| отдельные коллекции | `posts`, `posts_en` | явные схемы | дублирование схем, ад в sitemap/RSS |

**Рекомендация: параллельные каталоги + явный `translationKey`** во frontmatter
(дефолт — путь относительно корня локали). Ключ нужен, потому что из него собирается
взаимный `hreflang` (канон L-3: «если две страницы не ссылаются друг на друга, теги
игнорируются»), а также переводные slug'и.

```yaml
# content/ru/blog/kak-my-delaem-sajty.md
translationKey: how-we-build-sites     # общий для всех локалей
slug: kak-my-delaem-sajty              # локализованный URL — опция
```

#### 2.9.2. Политика

- URL-схема — **префикс пути**, дефолтная локаль без префикса (`/about`, `/en/about`) —
  канон L-1 (Google: subdirectory «Easy to set up, Low maintenance»).
- **Fallback-политики «показать русский текст под `/en/`» — нет.** Непереведённая
  страница под чужой локалью либо не существует (**404**), либо не публикуется вовсе.
  Дубль контента под двумя URL с разными `lang` — прямой вред: hreflang не подтвердится,
  а Google получит два почти одинаковых документа.
- `hreflang` выводится **из фактического набора переводов документа**, а не из списка
  локалей сайта. Для страницы без перевода — только self-ссылка (или вообще без alternate).
  `x-default` → версия на дефолтной локали.
- Никаких авто-редиректов по `Accept-Language` (канон L-4); допустим ненавязчивый баннер
  «есть версия на вашем языке».
- **Обязательно переводить** (если сайт двуязычный вообще): главная, услуги/продукт,
  контакты, «о компании», юридические тексты (политика ПДн — на языке аудитории, которая
  оставляет данные). Блог — по факту: лучше десять честно переведённых постов, чем сто
  машинных.
- Переводные slug'и — **MAY**; если включены, `translationKey` обязателен, а карта
  `slug ↔ translationKey` строится на билде и проверяется тестом на коллизии.
- UI-строки (кнопки, подписи) — отдельный слой i18n-каталогов; **не смешивать** с
  контентом: у них разные авторы и разная частота изменений.

### 2.10. Фиды, sitemap, редиректы, 404/410, канонический хост, staging

#### 2.10.1. RSS/Atom

- Один фид **на локаль и на тип контента, который реально обновляется**: `/rss.xml`,
  `/en/rss.xml`; для новостей и блога — раздельно, если это разные потоки.
- Динамический server route (абсолютные URL из `SITE_URL`), `Content-Type:
  application/rss+xml; charset=utf-8`, `Cache-Control: public, max-age=600`.
- Обязательно: `<atom:link rel="self" href="…">`, стабильные `<guid isPermaLink="true">`,
  `pubDate` в RFC-822, абсолютные ссылки в теле, ограничение — последние 20–50 записей.
- Автодискавери в `<head>`: `<link rel="alternate" type="application/rss+xml" title="…"
  href="/rss.xml">`.
- Полный текст vs анонс — решение проекта (`content.md`); дефолт шаблона — **анонс +
  ссылка** (меньше дублирования, меньше вес фида).
- Турбо-страницы Яндекса, которые раньше питались RSS, **закрыты** (канон 2.6) — фид
  делаем для читателей и агрегаторов, не для Яндекса.

#### 2.10.2. Sitemap

- `sitemap.xml` — **индекс**, шарды по типу и локали: `sitemap-pages-ru.xml`,
  `sitemap-blog-ru.xml`, `sitemap-blog-en.xml`, `sitemap-catalog.xml`.
  Порог шардирования — 50 000 URL / 50 МБ (канон I-11), но разделять по смыслу полезно
  раньше: в Search Console/Вебмастере видно, какой раздел проиндексирован.
- Источник — **контент-индекс** (см. §2.2.6) + таблица маршрутов из `rendering.md`
  (`indexable: yes`). Никаких «обошли сайт краулером на билде».
- `lastmod` — **только честный** (канон I-12). Источник: `updatedDate` во frontmatter.
  ⚠️ Git-дату файла взять в рантайме нельзя: `.git` в образ не попадает
  (`.dockerignore` SPA-шаблона содержит `.git` **[П]** — чтение репо). Варианты:
  (а) `updatedDate` в frontmatter — дефолт; (б) локальный скрипт `pnpm content:dates`
  проставляет её из `git log -1 --format=%cI -- <file>` и коммитит; (в) вычислять на
  билде до `docker build` и класть в `content-index.json`. Если даты нет — **элемент
  не выводится вовсе**.
- `changefreq`/`priority` — не выводить (канон I-13).
- hreflang в sitemap — можно (Google), но **не как единственный сигнал**: у Яндекса
  поддержка не подтверждена (канон I-11/2.6) ⇒ `<head>` обязателен.

#### 2.10.3. Редиректы как данные

```yaml
# content/redirects.yaml — черновик формата
- from: /uslugi/staraya-stranica      # ровно один путь, без домена и query
  to: /services/audit                 # корневой относительный или абсолютный (внешний)
  status: 301                         # 301 | 308 | 410
  note: 'переезд после редизайна 2026'
- from: /akcii/leto-2025
  status: 410                         # удалено навсегда, `to` не нужен
```

- Загружается сервером при старте в `Map`, применяется **до** роутинга, один хоп.
- Гейт (unit-тест + `pnpm check`): нет циклов; нет цепочек (`to` не является чьим-то
  `from`); `from` не совпадает с существующим маршрутом; `to` существует (или явно
  помечен внешним); нет дублей `from`; статусы только из белого списка.
- **Почему не в конфиге фреймворка**: у части фреймворков статические редиректы
  вырождаются в `meta refresh`. Astro дословно: *«When running `astro build`, Astro will
  output HTML files with the meta refresh tag by default»*, и *«If building to HTML files
  the status code is not used by the server»* **[П]**
  https://docs.astro.build/en/guides/routing/. Google такие редиректы понимает («Google
  Search interprets instant `meta refresh` redirects as permanent redirects»), но сам же
  рекомендует серверные: *«we recommend that you use a permanent server-side redirect
  whenever possible»* **[П]**
  https://developers.google.com/search/docs/crawling-indexing/301-redirects.
  ⇒ редиректы обслуживает **наш сервер**, а не билд.
- **Почему не в Traefik**: правила переезда URL — это знание проекта, оно должно
  ревьюиться в PR вместе с контентом и переезжать с образом; в инфре остаются только
  инфраструктурные редиректы (www→apex, http→https).

#### 2.10.4. 404 / 410 / soft-404

- Несуществующий документ → **404** с нормальной страницей (поиск по сайту, ссылки на
  разделы), `noindex`.
- Удалённый намеренно → **410** через `redirects.yaml` (Google: 404/410 — «stronger
  signals than blocking», канон 2.7).
- **Soft-404 запрещён**: «ничего не найдено» с кодом 200 — главный источник мусора в
  индексе. Гейт e2e: `/blog/net-takogo` → 404; `/xx/` → 404; страница 404 не содержит
  `<link rel=canonical>` на главную.
- Ошибка загрузки данных → **500** (`noindex`, без кеша), плановые работы → **503 +
  `Retry-After`** (канон B-6). Троттлинг — **429**, не 403 (канон B-4).

#### 2.10.5. Канонический хост и нормализация

- Один канонический хост (apex `${DOMAIN}`), `www` → **301** на Traefik
  (`redirectRegex`, `04` §3.6), http → https на entrypoint.
- В приложении — один нормализующий **308**: хвостовой слеш (`never`), нижний регистр
  пути, срезание неизвестных query-параметров у публичных страниц (канон I-5, I-6).
  Ровно один хоп: сначала нормализация, потом роутинг.
- `SITE_URL` — источник истины для абсолютных URL; на старте и при несовпадении с
  входящим `Host` — предупреждение в лог (ловит «забыли поменять env при клонировании
  среды»). **[?]**

#### 2.10.6. Staging-noindex (три независимых контура, канон I-15)

1. `ROBOTS_POLICY=noindex` в приложении → `X-Robots-Tag: noindex, nofollow` на всех
   HTML-ответах + `robots.txt` = `Disallow: /` (источник истины, тестируется в `pnpm check`).
2. Traefik `basicAuth` на staging-роутере (401 надёжнее любого заголовка).
3. Traefik `customResponseHeaders: X-Robots-Tag` на staging-роутере — **страхует статику
   и prerender-ответы**, до которых код приложения может не дотянуться.

Обратный гейт не менее важен: тест «на проде **нет** `noindex`» (иначе однажды выкатим
staging-конфиг в прод и тихо выпадем из индекса).

### 2.11. Производительность и бюджеты

#### 2.11.1. От чего отсчитывать: медиана веба 2025

Web Almanac 2025, глава Page Weight, медианы transfer size (**[П]**
https://almanac.httparchive.org/en/2025/page-weight, проверено 2026-09-15):

| ресурс | медиана mobile | медиана desktop | p90 mobile |
|---|---|---|---|
| страница целиком | **2 164 КБ** | 2 412 КБ | 8 337 КБ |
| HTML | **33 КБ** | 35 КБ | 151 КБ |
| CSS | 79 КБ | 83 КБ | 268 КБ |
| JavaScript | **646 КБ** | 708 КБ | 1 910 КБ |
| изображения | 911 КБ | 1 058 КБ | 6 288 КБ |
| шрифты | 23 КБ | 23 КБ | 80 КБ |

Это и есть «планка, ниже которой мы обязаны быть в разы»: контентная страница шаблона
должна весить примерно в 5–10 раз меньше медианного сайта, и главный вклад даёт не
героизм, а **отсутствие JS-фреймворка на контентных страницах**.

#### 2.11.2. Бюджеты шаблона

| что | цель | жёсткий потолок | чем меряется |
|---|---|---|---|
| HTML документа (несжатый) | ≤ **100 КБ** | **300 КБ** (алерт на 150) | e2e: `Buffer.byteLength(html)` — канон I-24 (лимит Googlebot 2 МБ, обрезка молчаливая) |
| CSS на странице (gzip) | ≤ **15 КБ** | 25 КБ | `size-limit` (`@size-limit/file`) на выходной css |
| JS на контентной странице (gzip) | **0 КБ** | **30 КБ** (островки: меню, поиск, consent) | Playwright: сумма тел `script`-ресурсов; `size-limit` на бандлы островков |
| JS третьих сторон (счётчик, капча) | **0 КБ** до согласия / до взаимодействия | **120 КБ** по проводу, и только после согласия | Playwright: сумма `script`-ответов с чужих origin'ов; тест «до согласия чужих скриптов нет» (§2.7.5) |
| шрифты на первую отрисовку | ≤ **60 КБ** (1–2 файла WOFF2) | 100 КБ | e2e + `size-limit` |
| LCP-изображение | ≤ **150 КБ** (AVIF) | 250 КБ | тест на `<img fetchpriority=high>`: `Content-Length` |
| страница целиком (transfer, без видео) | ≤ **400 КБ** | 800 КБ | Lighthouse `budget.json` (`resourceSizes`) |
| TTFB p75 (кеш-хит) | ≤ **50 мс** | 200 мс | smoke `curl -w '%{time_starttransfer}'`, RUM |
| TTFB p75 (кеш-промах, SSR) | ≤ **200 мс** | 400 мс | то же |
| CWV p75 mobile | LCP ≤ 2.5 с · INP ≤ 200 мс · CLS ≤ 0.1 | — | RUM + PSI (канон P-5) |
| Lighthouse CI (mobile, контентная страница) | performance ≥ **0.95**, seo = **1**, a11y ≥ **0.95**, best-practices ≥ 0.95 | — | отдельный CI-stage, не в `pnpm check` |

Порог `performance ≥ 0.95` для контентного сайта без JS — достижимый, а не косметический:
это и есть смысл выбора «HTML-first». Если он не берётся, значит в архитектуру протекло
что-то лишнее.

#### 2.11.3. Практики, которые дают эти цифры

- **Ноль JS по умолчанию**: интерактив — островами (меню-бургер, поиск, consent, фильтр
  каталога, форма). Каждый остров — отдельная строка в `size-limit`, добавление острова
  видно в диффе.
- CSS — **один внешний файл**, не инлайн (канон P-12: инлайн ест бюджет HTML и не
  кешируется между страницами). Для сайта на токен-слое Tailwind v4 15 КБ gzip — с запасом.
- Шрифты — §2.4; картинки — §2.3.
- **Никаких сторонних скриптов в `<head>` синхронно** (канон P-14): счётчики — после
  согласия и после `requestIdleCallback`/первого взаимодействия.
- `ETag` + 304 на HTML (кеш-хиты у краулеров дешевле для crawl budget).
- **View Transitions** (`@view-transition` для межстраничных переходов) — **MAY,
  прогрессивное улучшение**: cross-document VT поддержаны Chromium 126+ и Safari 18.2+,
  Firefox — частично/за флагом; MDN держит статус «Limited availability, explicitly not
  Baseline» **[П~]** (сводка по MDN/caniuse, 2026-09-15). Цена — несколько строк CSS,
  вреда для SEO нет (это CSS-переход, HTML не меняется); включать — по вкусу проекта,
  не в дефолт шаблона, и никогда через JS-роутер (иначе прощай «ноль JS»).
- **Speculation Rules** (`prefetch`, `eagerness: moderate`) — MAY, даёт мгновенные
  переходы без SPA; проверить, что не ломает счётчики и не удваивает просмотры.
- RUM: `web-vitals` (LCP/INP/CLS/FCP/**TTFB**) → `navigator.sendBeacon` на свой
  `/_vitals`-роут либо в Sentry; TTFB в SSR — первоклассная метрика (канон P-6).

### 2.12. Доступность как часть гейта

Минимум для контентного сайта (он же почти полностью пересекается с SEO — канон 2.10):

| уровень | что | где |
|---|---|---|
| **в `pnpm check`** | axe на компонентах-островах (меню, форма, диалог поиска, consent); unit-проверки `alt`/`aria` в UI-примитивах | Vitest + axe |
| **в `pnpm test:e2e`** | axe на 3–5 ключевых страницах (главная, пост, контакты, 404, каталог) в двух темах (light/dark) | Playwright + `@axe-core/playwright` |
| **в CI-stage LHCI** | `categories:accessibility ≥ 0.95` | Lighthouse CI |
| **чеклист релиза** (руками) | клавиатурный проход, skip-link, видимый фокус, контраст, масштаб 200 %, `prefers-reduced-motion`, читаемость без CSS | `/release` |

Инварианты, которые стоит зашить правилом (`.claude/rules/`), потому что автотест их
ловит плохо:

- ровно один `<h1>`, иерархия заголовков без скачков; лендмарки `header/nav/main/footer`,
  ровно один `<main>`;
- ссылка — `<a href>`, кнопка — `<button>`; «читать далее» без контекста запрещено
  (и для SEO: Google рекомендует описательный анкор);
- у каждого изображения — осмысленный `alt` (или `alt=""` для декоративного) и
  `width`/`height`;
- форма: `<label for>`, `aria-describedby` на ошибку, `aria-live` на результат отправки,
  ошибки текстом, а не только цветом;
- `prefers-reduced-motion` уважается всеми анимациями, включая view transitions;
- контент доступен **без JS** (это же требование канона I-1).

`pa11y-ci` — опция «сверху» (ещё один прогон Chrome в CI); при наличии axe в Playwright
он избыточен. Версии инструментов — §2.12.1.

   мажоры Vitest, вариант (в) выглядит честнее. **[?]**
3. **LHCI не кладётся в `pnpm check`** — и не только из-за времени прогона (это уже
   решено в §2.12), а потому что `@lhci/cli` отстаёт от Lighthouse и не декларирует
   поддержку Node: пин версии Node в образе CI-stage обязателен, а бюджеты живут в
   `budget.json`, который читается и standalone-Lighthouse'ом. Альтернатива на вырост —
   вызывать `lighthouse@13` напрямую с `--budget-path` и парсить JSON, оставив LHCI
   только ради его сервера отчётов. **[?]**
4. **`pa11y-ci` — опция «сверху»**, не дефолт: он даёт второй движок (HTML_CodeSniffer/axe
   на выбор), но и второй Chrome в CI.

### 2.13. Что приходит из strategy-репо и какие kinds нужны в `docs/stack`

#### 2.13.1. Контентный сайт в языке strategy

Канон strategy менять **не требуется** — контентный сайт в него ложится без натяжек
(проверено чтением `business-strategy-template/docs/projects/_template/**`, 2026-09-15):

| артефакт strategy | как выглядит для сайта | что из него выводит сайт-репо |
|---|---|---|
| `project/surface.md` | строка `type: web`, `lives-at: example.com` | сам факт поверхности; `SITE_URL`-дефолт |
| `interface/<surface>/who.md` | посетитель, клиент, соискатель | аудитория страниц; язык текстов |
| `interface/<surface>/situation.md` | «выбрать услугу», «оставить заявку», «прочитать кейс» | набор страниц и CTA |
| `interface/<surface>/data-items.md` | **`article`, `service`, `case`, `vacancy`, `faq-item`, `office`** — в языке заказчика | **типы контента** (коллекции) |
| `screens/<surface>/screen.md` | route/view + слоты + состояния (`empty`, `not-found`) | композиция страницы, состояния (в т.ч. «ничего не найдено» → 404) |
| `screens/<surface>/block.md` | hero, преимущества, карточки услуг, форма, футер | widgets/секции лендинга |
| `fsd/<surface>/entities.md` | `slug: article`, `source: article` (data-item), поля | Zod-схема коллекции контента |
| `fsd/<surface>/pages.md` | `path: /blog/:slug`, `guard: public`, `screen: post` | маршрут + запись в `rendering.md` |
| `fsd/<surface>/widgets.md` | `block` + ≥2 page-рефа | widget-слайсы |

Чего в каноне strategy нет и **не должно появиться**: SERP-копия, режим рендера,
`indexable`, размеры картинок, политика robots (аргументация — §2.1.3 + `05` §2.5).
Опциональный минимальный канон-PR (из `05` §2.5, остаётся в силе): две колонки в
`pages.md` — `indexable` (`yes|no`) и `freshness` (`static|periodic|live|per-user`) —
в языке смысла, без имён фреймворков. Без него `/scaffold` спрашивает интерактивно и
пишет ответ строкой в `rendering.md`.

⚠️ Отдельная находка (drift, чинить независимо от этой работы): канон `screens/README.md`
в strategy до сих пор описывает дерево компонентов в терминах манифеста **`@stit/ui`**
(`ui:Button`, `icons`-реестр, «craft библиотеки») **[П]** — при том что владелец
зафиксировал: внешняя DS не используется. Для контентного сайта это особенно заметно:
лендинг-блоки описываются `layout:`/`block:`-узлами, а `ui:`-словарь взять неоткуда.
Предложение (не в этой сессии): в каноне screens разрешить `ui:`-рефы **на проектный
`shared/ui`**, а не на внешний манифест.

#### 2.13.2. Какие kinds нужны контент-шаблону

База SPA-шаблона — 8 kinds; `telegram-bot-template` держит 11, то есть число kinds не
часть канона экосистемы (`05` §2.4). Для контент-first предлагаю **12**: 8 наследуемых
(часть — с правками) + 4 новых.

| kind | статус | почему |
|---|---|---|
| `service` | наследуется | + `infra-svc: site` (по нему `/release` печатает `make bump SVC=site`) |
| `runtime` | правится | Node-процесс: порт, graceful shutdown, `/healthz`, память, keep-alive |
| `config` | правится | `process.env` + **явный whitelist публичных ключей**; колонка «попадает в HTML?» |
| `routing` | наследуется | дерево маршрутов, layout'ы, guard'ы |
| **`content`** | **новый** | источник контента, коллекции и их схемы, локали контента, draft/preview, инвалидация |
| **`rendering`** | **новый** | режим на маршрут, кеш, статусы, где берётся абсолютный origin (развилка §2.2) |
| **`seo`** | **новый** | идентичность сайта, OG, JSON-LD, hreflang, robots, sitemap, верификации |
| **`images`** | **новый** | пайплайн картинок, форматы/ширины, хранение оригиналов, OG-генерация, бюджеты |
| `api` | правится | внешние источники данных (CMS/бэкенд), серверный vs браузерный base URL |
| `styling` | наследуется | токен-слой, темы, **шрифты** (или отдельной секцией) |
| `observability` | правится | серверная сторона + RUM с TTFB |
| `dependencies` | наследуется | другая базовая подборка |

**Про `forms.md`**: отдельный kind заводить **не рекомендую** — форма на контентном сайте
это (а) endpoint, (б) антиспам-политика, (в) доставка (Telegram/SMTP/бэкенд), (г) юридика
(согласие на ПДн). Пункты (а)–(в) укладываются в `api.md` (секция «Входящие обработчики»),
(г) — в `seo.md`/`content.md` (юридические страницы). Если у проекта форм много и они
разные (заявка, расчёт, запись, загрузка файла) — завести `forms.md` как **проектное
расширение**, а не как канон шаблона. Порог для пересмотра: > 3 разных обработчиков.

**Про `search.md`**: не нужен — поиск это одна строка в `content.md` (есть/нет, движок,
индексы по локалям) и одна в `rendering.md` (`/search` — `dynamic`, `noindex`).

Цена: интервью `/stack-deep-dive` растёт на 4 волны. Митигация — все четыре формы
поставляются предзаполненными дефолтами шаблона; реально обязательных ответов немного:
канонический хост, бренд, набор локалей, типы контента, источник контента.
Порядок волн: `service → runtime → config → content → routing → rendering → seo →
images → api → styling → observability → dependencies` (каждая следующая опирается на
предыдущую: `rendering` нужен перечень маршрутов и типов контента; `seo` — `indexable`;
`images` — типы контента).

#### 2.13.3. Дельта агентной обвязки под контент-first

| артефакт | дельта |
|---|---|
| `.claude/rules/content-pipeline.md` (**новое**, path-scope `content/**`, `src/shared/content/**`) | коллекция = Zod-схема; обязательные поля frontmatter; `draft` не публикуется; компиляция на билде; `translationKey` для переводов; картинки контента — рядом с текстом |
| `.claude/rules/seo-invariants.md` (**новое**, path-scope `src/pages/**`, `src/shared/seo/**`) | абсолютный self-canonical; директивы robots не смешивать; hreflang взаимный и только для существующих переводов; JSON-LD только про видимое; честные 404/410; `meta refresh` запрещён; в теле — относительные ссылки |
| `.claude/rules/cache-and-rendering.md` (**новое**) | четыре режима; ключ кеша без cookie/UA; приватное не кешируется; инвалидация = релиз/TTL/вебхук; `X-Cache` |
| `.claude/rules/tests-pipeline.md` | + раздел «контентные гейты»: размеры HTML/CSS/JS, axe на ключевых страницах, e2e на статусы и сырой HTML |
| `.claude/rules/env-local.md` | переписывается: `process.env` сервера + явный публичный whitelist; `SITE_URL` — runtime, не build-time |
| `/stack-deep-dive` | +4 волны (`content`, `rendering`, `seo`, `images`), cross-kind-проверки: каждая page из FSD-карты есть в `rendering.md`; `indexable` не противоречит `guard`; env из новых kinds доехали в `config.md` |
| `/scaffold` | новые kinds: `collection` (коллекция контента: схема + страницы списка/детали + записи в `rendering.md`/`seo.md`), `route` (server route: фид, sitemap-шард, обработчик формы); для `page` — вопросы про режим, indexable, JSON-LD, участие в sitemap |
| `/de-template` | + прун `content/**` демо-контента и демо-`site.yaml`, замена `SITE_URL`/бренда, удаление демо-OG, пересборка `robots.txt`-дефолтов, удаление выключенного модуля кабинета |
| `/release` | + SEO-чек-лист (канон §5) и проверка «контент, который должен был опубликоваться, попал в образ» (в git-режиме это не очевидно) |
| **`/content-audit`** (**новый, опционально**) | прогон по контент-индексу: документы без `description`, дубли title, битые внутренние ссылки, картинки без `alt`, «сироты» (нет входящих ссылок), просроченный `updatedDate`, черновики, забытые в `main` |

### 2.14. Reference-слайсы контент-first шаблона

Принцип прежний (`05` §2.7): **каждый механизм — ровно один раз**, весь набор удаляется
`/de-template`, набор читается как учебник. Но состав пересобран под контент-first: вместо
«SPA с блогом» — «сайт, у которого есть кабинет-опция».

```
src/pages/                                   что учит
├── index                    лендинг: hero + 3 поста + CTA
│                            · режим static · WebSite + Organization JSON-LD
│                            · LCP-картинка (fetchpriority, srcset) · ноль JS
├── about                    «о компании» · LocalBusiness JSON-LD (адрес, часы, гео)
│                            · BreadcrumbList · карта — статичная картинка-ссылка,
│                              а не внешний iframe (учит цене третьей стороны)
├── blog/index               список: пагинация ?page=N (self-canonical на каждой),
│                            фасет ?tag= → noindex,follow · режим cached (SWR)
├── blog/$slug               пост: Article JSON-LD · OG-картинка из шаблона ·
│                            хлебные крошки · lastmod · <picture> AVIF/WebP ·
│                            честный 404 на неизвестный slug · «читать далее» — нет
├── catalog/index            каталог из API: серверная фильтрация обычными <a href="?…">,
│                            остров-фильтр только улучшает · режим cached · пустой
│                            результат — 200 с текстом, несуществующий фасет — 404
├── catalog/$slug            карточка: Product/Offer JSON-LD (по требованию) ·
│                            картинки из внешнего источника → runtime-ресайз /img/*
├── contacts                 форма: no-JS Post/Redirect/Get · honeypot + time-trap ·
│                            origin-check · шов капчи · согласие на ПДн со ссылкой
├── contacts/spasibo         страница «спасибо»: public, но **noindex** (учит: public ≠ indexable)
├── legal/privacy            политика обработки ПДн: обязательна, если есть форма ·
│                            static · индексируется
├── search                   поиск по сайту: статический индекс · noindex, follow ·
│                            не в sitemap
├── now                      per-request демонстрация: `dynamic`, no-store, noindex
├── account (опция)          кабинет: client-only + guard · noindex · private, no-store ·
│                            поставляется выключенным (ENABLE_ACCOUNT=false)
└── 404 / 500                честные коды, полезная 404 (поиск + разделы)

server routes/
├── robots.txt               политика из seo.md + ROBOTS_POLICY (staging)
├── sitemap.xml + шарды      индекс + sitemap-<type>-<locale>.xml из контент-индекса
├── rss.xml, en/rss.xml      фид на локаль
├── og/[key].png             генерация OG-картинок с дисковым кешем
├── img/*                    runtime-ресайз внешних картинок (allowlist источников)
├── api/contact              обработчик формы (POST, 303 на /contacts/spasibo)
├── api/preview[, /exit]     draft-режим по HMAC-токену
├── internal/revalidate      вебхук инвалидации (HMAC)
└── healthz                  200 ok, без зависимостей

src/widgets/
├── site-header              nav, переключатель языка и темы, skip-link
├── site-footer              контакты, юридические ссылки, соцсети (sameAs → JSON-LD)
├── breadcrumbs              видимые крошки + BreadcrumbList из одного массива
├── post-card                карточка поста (список, лендинг, «похожие») — ≥2 page-рефа
└── cookie-banner            островок: согласие → загрузка счётчиков (2 категории)

src/features/
├── contact-form             прогрессивное улучшение поверх рабочей HTML-формы
├── catalog-filter           остров-фильтр поверх серверных ссылок
├── site-search              островок поиска (модалка + статический индекс)
└── theme                    light/dark из cookie (SSR-совместимо, без FOUC)

src/entities/
├── article                  коллекция git-контента: схема, индекс, teaser, Article JSON-LD
├── product                  контент из API: схема ответа, маппер, Product JSON-LD
└── company                  данные организации (адрес, часы, телефоны) → LocalBusiness,
                             футер, страница контактов — единый источник

src/shared/
├── seo/                     meta, canonical, hreflang, json-ld, robots, sitemap, indexnow
├── content/                 ContentSource (fs|http), схемы коллекций, компиляция на билде
├── images/                  srcset-хелпер, <Picture>, og-генератор, кеш
├── ui/                      примитивы на собственном токен-слое
├── i18n/ config/ lib/ observability/
```

Пояснения к спорным местам:

- **Почему каталог из API, а не вторая git-коллекция.** Нужно показать второй источник
  (`httpSource`), инвалидацию по вебхуку и runtime-ресайз чужих картинок — иначе шаблон
  учит только «сайт-визитке».
- **Почему `/contacts/spasibo` отдельной страницей.** Учит PRG и тому, что `public` ≠
  `indexable`; заодно даёт цель для аналитики (конверсия) без «спасибо» в модалке,
  которую нельзя измерить и нельзя открыть по ссылке.
- **Почему `legal/privacy` в наборе.** Без политики обработки ПДн форма на РФ-сайте
  нелегитимна (§2.7.3); reference-набор должен научить, что форма и политика приезжают
  вместе.
- **Почему `account` выключен по умолчанию.** Кабинет — не главный сценарий; но одна
  приватная страница нужна, чтобы показать связку `guard` + `noindex` +
  `private, no-store` + client-only. Включается флагом, удаляется `/de-template`.
- **Чего в наборе нет намеренно**: второй блог-сущности, «похожих постов» из ML,
  комментариев, подписки на рассылку (дублирует урок формы), внешних карт и виджетов
  соцсетей (учит ровно обратному тому, что нужно для CWV).
- **Mock/сценарии данных** для `httpSource` — те же имена, что в SPA-шаблоне
  (`empty | populated | error`), чтобы родство читалось.

## 3. Референс-архитектура одной картинкой

### 3.1. Поток контента: от источника до HTML

```
╔═ СБОРКА ОБРАЗА (машина разработчика; CI-раннера в экосистеме нет) ══════════════╗
║                                                                                ║
║  content/ru/**.md(x)  ──┐                                                      ║
║  content/en/**.md(x)  ──┤ Zod-схемы коллекций (ошибка схемы = красная сборка)   ║
║  content/redirects.yaml ┤                                                      ║
║  content/assets/**      │                                                      ║
║           │             ▼                                                      ║
║           │      компиляция MD→HTML (+ подсветка кода, заголовки, TOC)          ║

                           │  docker build  →  git.stit.tech/<org>/site:vX.Y.Z
                           ▼
╔═ КОНТЕЙНЕР (один Node-процесс; env: SITE_URL, ROBOTS_POLICY, CONTENT_SOURCE…) ══╗
```

Читается так: **контент компилируется на билде, страница собирается на запрос, абсолютные
URL приходят из env контейнера, кеш живёт в процессе и инвалидируется релизом, TTL или
вебхуком.** Это и есть ответ на развилку §2.2.

```

│   ├── assets/**                  оригиналы картинок контента

│   └── site.yaml                  данные организации (адрес, часы, телефоны, sameAs)
├── src/
│   ├── app/                       вход, layout, провайдеры, стили/токены, init

│       ├── seo/                   meta · canonical · hreflang · json-ld · robots · sitemap · indexnow
│       ├── content/               ContentSource (fs|http) · схемы коллекций · компиляция
│       ├── images/                srcset · <Picture> · og-генератор · дисковый кеш
│       ├── ui/ lib/ config/ i18n/ observability/
```

FSD-инварианты те же (`app → pages → widgets → features → entities → shared`, public API
через `index.ts`, Steiger). Новое относительно SPA-шаблона — `content/` **вне** `src/`
(это не код и не слайс: у него другой автор и другой цикл жизни) и два новых сегмента
sliceless-слоя `shared`: `seo/` и `content/`.

## 4. Черновики новых kinds `docs/stack/_templates/*`

Форма — как у существующих восьми (frontmatter `id/kind/name/status`, H1 = kind,
обязательная секция `Generates`, финальная «Открытые вопросы»). Черновики намеренно
**не называют библиотек** в шапках таблиц: конкретика подставляется после выбора
фреймворка (потоки 07–11), решение формулируется в языке проекта.

### 4.2. `docs/stack/_templates/rendering.md`

````markdown
---
id: stack.rendering
kind: rendering
name: rendering
status: draft
---

# rendering

## Режимы

| режим | когда | что значит для запроса |
|---|---|---|
| `static` | меняется не чаще релиза | HTML вычислен заранее, отдаётся из памяти/файла |
| `cached` | общий для всех, меняется чаще релиза | рендер на запрос + кеш процесса (TTL + SWR) |
| `dynamic` | зависит от запроса, кеш запрещён | рендер на каждый запрос |
| `client` | персональное/интерактивное, не для поиска | каркас + данные на клиенте |

## Карта маршрутов

Перечень маршрутов — из `pages.md` FSD-карты поверхности. Инвариант: `guard ≠ public`
⇒ `indexable: нет` + `private, no-store` + нет в sitemap.

| path | режим | TTL/SWR | Cache-Control | indexable | в sitemap |
|---|---|---|---|---|---|
| `/` | `static` | — | `no-cache` + ETag | да | да |
| `/about` | `static` | — | `no-cache` + ETag | да | да |
| `/blog` | `cached` | 300/3600 | `no-cache` + ETag | да | да |
| `/blog/<slug>` | `static` | — | `no-cache` + ETag | да | да (из контента) |
| `/blog?tag=` | `cached` | 300/3600 | `no-cache` | **нет** (фасет) | нет |
| `/catalog` | `cached` | 300/3600 | `no-cache` | да | да |
| `/search` | `dynamic` | — | `no-store` | нет | нет |
| `/contacts/spasibo` | `static` | — | `no-cache` | **нет** | нет |
| `/account/**` | `client` | — | `private, no-store` | нет | нет |

## Абсолютные URL и один образ на все среды

| поле | значение |
|---|---|
| источник origin | `SITE_URL` (runtime env) |
| как origin попадает в заранее собранный HTML | `нет prerender (рендер на запрос)` \| `штамповка плейсхолдера при старте` \| `build-arg (только одна среда)` |
| правило | абсолютные URL — только в `<head>`, JSON-LD, фидах, sitemap; в теле — корневые относительные |

## Нештатные коды

| ситуация | код |
|---|---|
| неизвестный документ/параметр | `404` |
| удалено навсегда (`redirects.yaml`) | `410` |
| переезд URL | `301` |
| нормализация (регистр, слеш) | `308` |
| ошибка данных | `500` (`noindex`, без кеша) |
| плановые работы | `503 + Retry-After` |
| троттлинг | `429` |

## Кеш и инвалидация

| поле | значение |
|---|---|
| где живёт кеш | память процесса (LRU, `CACHE_MAX_ITEMS`) |
| ключ | метод + путь + локаль; cookie/UA/неизвестные query — **не входят** |
| заголовок наблюдаемости | `X-Cache: HIT \| STALE \| MISS \| BYPASS` |
| прогрев после старта | список «горячих» URL, фоном, не блокирует `/healthz` |
| инвалидация | релиз · TTL/SWR · `POST /internal/revalidate` · `POST /internal/cache/flush` |

## Streaming

| поле | значение |
|---|---|
| стриминг ответа | `выключен` \| `включён, кроме ботов` |
| правило | весь `<head>` и основной контент — в первом чанке (канон P-1/P-3) |

## Generates

- конфиг сборки (что предрендерится) и пер-маршрутные флаги режима
- `src/pages/**` — `head()`, загрузчики, коды ответов
- слой кеша и `X-Cache`, прогрев при старте
- заголовки кеширования (и их зеркало в Traefik)
- `e2e/seo.spec.ts` — коды, размеры HTML, наличие контента без JS
- `config.md` — env `SITE_URL`, `CACHE_*`, `REVALIDATE_SECRET`

## Открытые вопросы

- _что_
````

````markdown
---
id: stack.seo
kind: seo
name: seo
status: draft
---

# seo

## Идентичность сайта

| поле | значение |
|---|---|
| канонический хост | `https://<domain>` — один; `www` → 301 |
| `SITE_URL` | runtime env, абсолютный origin без хвостового слеша |
| бренд | _<Название>_ |
| title-шаблон | `%s — <Бренд>`; главная — без суффикса |
| дефолтный `description` | _<70–170 символов>_ |
| дефолтная OG-картинка | `/og/default.png`, 1200×630 |
| иконки | `favicon.ico` 32×32 · `icon.svg` · `apple-touch-icon.png` 180×180 · manifest |
| тип организации | `Organization` \| `LocalBusiness` (адрес, часы, гео — из `content/site.yaml`) |

## Социальные карточки

- OG: `type`, `title`, `description`, `url`, `image` (+ `width`/`height`/`alt`),
  `site_name`, `locale` (+ `locale:alternate`).
- `twitter:card` = `summary_large_image` при наличии картинки.
- Источник картинки страницы: _поле контента / генератор `/og/<key>.png` / дефолт_.

## Структурированные данные (JSON-LD)

| тип | где | источник полей |
|---|---|---|
| `Organization`/`LocalBusiness` | все страницы | `content/site.yaml` |
| `WebSite` | только корень домена | этот артефакт |
| `BreadcrumbList` | глубже первого уровня | иерархия маршрута (widget `breadcrumbs`) |
| `Article` | посты | frontmatter документа |
| _`Product`/`Event`/`JobPosting`/`VideoObject`_ | _где_ | _откуда_ |

Не генерировать по умолчанию: `FAQPage`, `HowTo`, `SearchAction` (rich results сняты),
`meta keywords` — никогда.

## Локали и hreflang

| locale | URL | роль |
|---|---|---|
| `ru` | `/…` | default, `x-default` |
| `en` | `/en/…` | supported |

Политика: alternate выводится **только для реально существующих переводов**, взаимно;
canonical — внутри локали; авто-редиректов по `Accept-Language` нет.

## robots-политика

| агент | политика |
|---|---|
| `*` | allow; `Disallow:` `/search`, `/api/`, `/internal/`, `/account/`, `/*?*sort=`, `/*?*tag=` |
| поисково-ответные AI (`OAI-SearchBot`, `Claude-SearchBot`, `PerplexityBot`) | allow |
| обучающие AI (`GPTBot`, `ClaudeBot`, `Google-Extended`, `Applebot-Extended`, `CCBot`, `Bytespider`) | `AI_TRAINING=allow \| deny` — **решение владельца сайта** |
| `Clean-param` (Яндекс) | `ref&from&openstat&<проектные>` |

Не-prod: `ROBOTS_POLICY=noindex` ⇒ `X-Robots-Tag: noindex, nofollow` + `Disallow: /`.
`Host`/`Crawl-delay` не генерировать (мертвы у Яндекса).

## Sitemap

| шард | источник | lastmod |
|---|---|---|
| `sitemap-pages-<locale>.xml` | маршруты `rendering.md` с `indexable: да` | дата релиза \| — |
| `sitemap-blog-<locale>.xml` | контент-индекс коллекции | `updatedDate` документа |
| `sitemap-catalog.xml` | API | `updatedAt` сущности |

Индекс `sitemap.xml` ссылается на шарды; `changefreq`/`priority` не выводятся;
`lastmod` — только честный, иначе не выводится.

## Фиды

| фид | что | локаль |
|---|---|---|
| `/rss.xml` | последние 20 постов, анонсы | `ru` |
| `/en/rss.xml` | то же | `en` |

## Верификация и уведомление поисковиков

| система | механизм | значение |
|---|---|---|
| Google Search Console | meta `google-site-verification` | env, пусто ⇒ тег не выводится |
| Яндекс.Вебмастер | meta `yandex-verification` | env |
| IndexNow (Яндекс/Bing) | ключ-файл `/<key>.txt` + submit при публикации | `INDEXNOW_KEY`, опционально |
| Яндекс.Метрика | id счётчика (обход по счётчику включается в Вебмастере) | env |

## Generates

- `src/shared/seo/*` — meta, canonical, hreflang, json-ld, robots, sitemap, indexnow
- корневой layout — дефолтный `head()` + `Organization`
- server routes `/robots.txt`, `/sitemap*.xml`, `/rss.xml`, `/<key>.txt`
- `e2e/seo.spec.ts` — canonical/robots/hreflang/JSON-LD/OG/статусы/размер HTML
- `config.md` — env `SITE_URL`, `SITE_NAME`, `ROBOTS_POLICY`, `AI_TRAINING`,
  `*_VERIFICATION`, `INDEXNOW_KEY`, `METRIKA_ID`
- чек-лист релиза `/release` (Rich Results Test, валидатор Яндекса, Вебмастер)

## Открытые вопросы
````

### 5.1. Требуют решения владельца (архитектурные развилки)

| # | Вопрос | Варианты | Цена ошибки |
|---|---|---|---|
| R-1 | **Как абсолютный origin попадает в заранее собранный HTML** (§2.2.3) | D (SSR+кеш, дефолт) · C (штамповка при старте) · A (build-arg, одна среда) | при A — «в проде образ, который не тестировали»; при C — забытый плейсхолдер в выдаче; при D — холодный кеш после релиза |
| R-2 | **Источник контента по умолчанию** (§2.1) | git (рекомендация) · CMS в self-host · контент-API своего бэкенда | CMS = +контейнер +БД +бэкап +роут на том же VPS, и это навсегда |
| R-3 | **Публикация = релиз?** При git-контенте редактор не может опубликовать без пересборки образа | принять (у сайтов с редкими правками) · CMS-поверх-git + автосборка · headless CMS | несоответствие ожиданиям заказчика обнаруживается после сдачи |

| R-5 | **Капча на формах** — нужна ли и какая (§2.6) | honeypot+time-trap только · + Яндекс SmartCaptcha · + Turnstile/hCaptcha | внешняя капча = внешняя зависимость и потенциальная недоступность для части аудитории |
| R-6 | **Аналитика и согласия** (§2.7) | только Метрика · Метрика+GA4 · self-host (Plausible/Umami) | юридические требования РФ + вклад в INP |

### 5.3. Принятые компромиссы (документировать, не чинить)

- Кеш HTML холодный после каждого релиза — сознательный размен на отсутствие ручной
  инвалидации (наследуется из `04` §3.3).
- Горизонтального масштабирования нет (`container_name` в инфра-каноне); кеш и дисковые
  кеши — на процесс.
- Без CDN 103 Early Hints недоступны (Traefik OSS не проксирует, `04` §2.5), `s-maxage`
  не работает — остаются `no-cache` + ETag + кеш процесса.
- Публикация git-контента = релиз образа. Для сайтов с ежедневными новостями это
  неприемлемо — там сразу (б)/(в).

## A. Метаданные страницы

### A.1 `<title>` и `<meta name="description">`

**Официальная позиция Google (Search Central, актуально на 2026):**

- Жёсткого лимита длины `<title>` нет: *"there's no limit on how long a `<title>` element can be"* — Google обрезает title в выдаче по ширине устройства, не по числу символов. **[проверено: https://developers.google.com/search/docs/appearance/title-link]**
- То же самое для description: *"There's no limit on how long a meta description can be, but the snippet is truncated in Google Search results as needed, typically to fit the device width."* Управлять максимальной длиной сниппета можно через `<meta name="robots" content="max-snippet:[number]">`. **[проверено: https://developers.google.com/search/docs/appearance/snippet]**
- Значит **все конкретные цифры символов/пикселей — это фольклор третьих лиц** (SEO-индустрия), а не спецификация Google. Разграничение:

| Метрика | Официально от Google | Практика индустрии (folklore, но полезно) |
|---|---|---|
| `<title>` desktop | нет цифры, «обрезается по ширине» | ~50–60 символов / ~500–600px **[вторично: множество SEO-блогов 2026, согласованно]** |
| `<meta description>` desktop | нет цифры | ~120–158 символов / ~920px **[вторично: агрегированные данные 2026]** |
| `<meta description>` mobile | нет цифры | ~120 символов / ~680px **[вторично]** |

Практическая деталь про pixel-ширину: у Google моноширинный расчёт не используется — каждая буква имеет свою пиксельную ширину («W» ≈ 11px, «i» ≈ 3px), поэтому символьный лимит — грубая эвристика **[вторично, но технически корректно и многократно подтверждено]**.

**Рекомендации Google по содержанию title** **[проверено: https://developers.google.com/search/docs/appearance/title-link]**:
- Уникальный, описательный, немноголословный `<title>` на каждой странице; не «Home»/«Profile».
- Не keyword-stuffing («Foobar, foo bar, foobars…») и не одинаковый boilerplate на разных страницах.
- Бренд — в начале или в конце через разделитель (`-`, `:`, `|`): `<title>ExampleSocialSite: Sign up for a new account.</title>` — это прямо обосновывает паттерн `%s | Site`.
- Язык/письменность title должны совпадать с языком контента страницы (важно для ru/en разделения в проекте — title на странице `/en/...` должен быть на английском, без транслитерации).

**Почему Google переписывает title** (rewrite title link) **[проверено: тот же URL]** — Google подменяет `<title>`, если:
1. в теге нет ключевой информации (half-baked title);
2. title устарел относительно контента страницы;
3. title неточен / не описывает страницу;
4. на странице нет ясного единственного заголовка (несколько одинаково жирных H1/H2);
5. язык/письменность title не совпадает с языком контента;
6. дублирование названия сайта — может быть убрано, если сайт уже показан отдельно.

Источники, которые Google использует для title-link (шире, чем просто `<title>`): сам `<title>`, видимый заголовок страницы, `<h1>`, `og:title`, крупный стилизованный текст, anchor text входящих ссылок, `WebSite` structured data **[проверено: там же]**. Важное для проекта следствие: **`og:title` — не только про соцсети, Google тоже может взять его как источник title link**, поэтому в SSR-хелпере `og:title` и `<title>` должны генерироваться из одного и того же значения по умолчанию (allow override по отдельности).

Отдельно подтверждено: в 2026 Google тестирует **AI-генерируемые title-ссылки** прямо в органической выдаче — ещё один аргумент писать «естественный», не keyword-stuffed title, потому что модель Google всё равно может его переформулировать. **[вторично: searchenginejournal.com, декабрь 2025 update документации]**

### A.2 Open Graph — канон ogp.me

**[проверено: https://ogp.me/]**

Обязательные теги (4 штуки) для любой страницы:
- `og:title`
- `og:type`
- `og:image`
- `og:url` — канонический постоянный URL объекта

Полезные опциональные:
- `og:description`
- `og:site_name`
- `og:locale` (формат `language_TERRITORY`, дефолт `en_US`; для проекта — `ru_RU` / `en_US`)
- `og:locale:alternate` (массив — на каждой языковой версии страницы перечислить остальные локали)
- `og:determiner`, `og:audio`, `og:video`

Структурированные свойства `og:image` (аналогично `og:video`, кроме `og:audio` — только 3 первых): `og:image:url`, `og:image:secure_url`, `og:image:type`, `og:image:width`, `og:image:height`, `og:image:alt`.

Сама спецификация ogp.me **не задаёт обязательных числовых размеров og:image** — там просто демонстрационный пример 400×300. Индустриальный стандарт размера — отдельный вопрос (см. ниже), это не часть протокола.

**og:image — практические требования (индустриальные, не из ogp.me):**
- Рекомендуемый размер: **1200×630px** (соотношение 1.91:1) — общий знаменатель для Facebook/X/LinkedIn/Discord/Slack/WhatsApp/iMessage. **[вторично, но кросс-платформенно согласовано: несколько независимых 2026-гайдов]**
- Минимум для крупного превью — около 600×315; абсолютный минимум для показа изображения вообще — 200×200. **[вторично]**
- Указывать `og:image:width`/`og:image:height` — помогает потребителю рендерить превью без скачивания файла для замера. **[вторично, но логично и подтверждено практикой Facebook Sharing Debugger]**
- **og:image должен быть абсолютным URL** (`https://...`), не относительным — большинство краулеров (в т.ч. Facebook/X) не гарантированно резолвят относительные пути против base URL; на практике многие консьюмеры вообще не резолвят. **[вторично, но многократно подтверждено практикой/багрепортами: github issues jitsi-meet #6031, vikejs/vike #2596, immich #11081]**. То же самое стоит соблюдать и для `og:url`.
- Вес файла — практический потолок у большинства консьюмеров в районе единиц МБ (Facebook гоняет до ~8MB, VK — до 5MB, см. A.4); в SSR-шаблоне стоит держаться до ~1MB для скорости анфёрлинга ботами.

### A.3 Twitter/X Cards

Официальная страница `developer.x.com/en/docs/x-for-websites/cards/overview/markup` при прямом фетче отдаёт **HTTP 402 Payment Required** — по всей видимости, доступ к части devcommunity/докам X в 2026 требует авторизации/биллинга аккаунта разработчика (X в феврале 2026 полностью перешла на pay-per-use API без бесплатного тира) **[проверено частично: https://developer.x.com/en/docs/x-for-websites/cards/overview/markup возвращает 402; контекст pay-per-use — https://gigazine.net/gsc_news/en/20260209-x-api-pay-per-use/]**. Собственно контент markup-страницы восстановлен по вторичным источникам:

- Типы карточек, актуальные в 2026: **`summary`** и **`summary_large_image`** — практически единственные общеупотребимые (player/app — нишевые, для видео/подкастов и мобильных приложений). **[вторично: devcommunity.x.com треды 2026, codeshack.io генератор]**
- Минимальный набор: `twitter:card` (обычно `summary_large_image`) + `twitter:image`. **Если на странице уже есть OG-теги, X использует их как fallback для title/description** — то есть `twitter:title`/`twitter:description` можно не дублировать. **[вторично, но это консистентное и давнее поведение Twitter Cards, широко задокументированное]**
- Полный список тегов (реконструирован): `twitter:card`, `twitter:title`, `twitter:description`, `twitter:image`, `twitter:image:alt`, `twitter:site`, `twitter:creator`; для player-карточек — `twitter:player`, `twitter:player:width`, `twitter:player:height`.
- Важный практический нюанс: если изображение меньше **300×157px**, X молча понижает `summary_large_image` до `summary`, независимо от указанного тега. **[вторично: devcommunity.x.com]**
- **Twitter Card Validator официально не существует с 2022 года** (задепрекейчен при ребрендинге в X); в 2026 нет замены от самой X — только сторонние инструменты (socialrails, tweetpik, sitechecker и т.п.), давать на них ссылку в документации проекта нет смысла, тестировать лучше через реальный шаринг или через Facebook Sharing Debugger (для OG-части) + LinkedIn Post Inspector. **[вторично, множественные независимые источники сходятся]**
- Ещё один нюанс 2023–2024: X несколько раз включал/выключал отображение заголовка (headline) поверх картинки в карточке, из чисто продуктовых (эстетических) соображений Маска — это означает, что **полагаться только на `twitter:*` рискованно**: практический вывод для проекта — генерировать `og:image`/`twitter:image` с текстом заголовка, запечённым прямо в картинку (см. A.5), чтобы не зависеть от того, показывает ли X текстовый заголовок отдельно. **[вторично: techcrunch.com архив 2023-2024, но сам факт нестабильности поведения важен методологически]**

Вывод для канона: в SSR-хелпере `twitter:card=summary_large_image` + `twitter:image` (можно = og:image) достаточно; отдельные `twitter:title/description` — опциональны (fallback на OG).

### A.4 Превью в мессенджерах

**Telegram:**
- Клиент Telegram вытягивает `og:title`, `og:description`, `og:image` (и `<title>` как fallback) через собственный краулер (упоминается как webPage/messageMediaWebPage в MTProto-схеме). **[проверено косвенно: https://core.telegram.org/constructor/webPage — сам механизм превью официально задокументирован на уровне протокола, явно говорится, что для описания используются в т.ч. «OpenGraph descriptions»]**
- Официального публичного документа «вот полный список og-тегов и лимитов на вес og:image, которые понимает Telegram» **не существует** — практика реверс-инжинирена сообществом. **[предположение: официальной пользовательской доки нет, только протокольный уровень core.telegram.org]**
- Кеш превью на стороне Telegram **не имеет задокументированного TTL** и может висеть сколь угодно долго; уже отправленные в чаты превью не обновляются никогда (заморожены на момент отправки). Обновить кэш для будущих шарингов — через бота **@WebpageBot**: отправить ему целевой URL → он предложит обновить/показать текущее превью. **[вторично, но многократно и давно подтверждённая практика; официальной альтернативы (типа API-эндпоинта invalidate) Telegram не предоставляет]**
- **Instant View** — отдельная опциональная фича (не связана напрямую с og-тегами превью-карточки, обычная og-разметка её не включает): нужен собственный IV-шаблон, регистрируемый через https://instantview.telegram.org/ . Для типового SSR-SPA-сайта не является приоритетом — это фича для статей/новостных площадок. **[проверено, что механизм существует: https://core.telegram.org/constructor/webPage упоминает WebPageAttribute для instant view; сам портал шаблонов — instantview.telegram.org]**

**ВКонтакте:**
- VK разбирает Open Graph: `og:title`, `og:description`, `og:image`. Есть указания (не 100% официально подтверждённые прямой докой) на VK-специфичный тег **`vk:image`** как приоритетный оверрайд над `og:image`, если он присутствует. **[вторично, средняя уверенность: qna.habr.com обсуждения; официальную страницу dev.vk.com с явным перечнем vk:* тегов найти не удалось]**
- Требования к изображению-сниппету при прикреплении ссылки: **соотношение сторон 1:1 или 5:2, минимальная ширина 500px**; если картинка меньше 160px по любой стороне (или к посту прикреплены другие вложения) — используется уменьшенная версия 150×83. Форматы: JPG/PNG/BMP/TIF/GIF (без анимации), **максимум 5MB**. **[вторично: агрегированные требования VK 2026, технически конкретно и правдоподобно, но без прямой ссылки на официальную страницу dev.vk.com]**
- VK-краулер представляется как `Mozilla/5.0 (compatible; vkShare; +http://vk.com/dev/Share)` — можно детектить в серверных логах для отладки. **[вторично: habr qna]**
- **Сброс кэша страницы** — официальный метод VK API `pages.clearCache`, вызывается как `https://api.vk.com/method/pages.clearCache?url=...&access_token=...` (нужен access_token сообщества, получаемый в настройках сообщества → «Работа с API»). Ранее также был человеко-читаемый инструмент «Отладка страниц» на dev.vk.com/dev/pages.clearCache — прямой фетч `dev.vk.com` из этой сессии недоступен («Claude Code is unable to fetch from dev.vk.com»), поэтому текущий UI-путь инструмента **не перепроверен напрямую**, но сам метод API официально документирован в экосистеме VK. **[частично проверено: метод API подтверждён множественными вторичными источниками, но не прямым фетчем dev.vk.com; помечаю как предположение по части «сейчас это называется именно "Отладка страниц"» — возможно переименовано]**

**MAX (мессенджер VK, экс-anonymous/Ростелеком-инициатива):**
- Официальная документация для разработчиков — **dev.max.ru/docs-api**. Прямой просмотр её раздела про отправку сообщений (`NewMessageBody`, `POST /messages`) **не содержит упоминаний og-тегов, превью ссылок, генерации сниппетов** — то есть либо фича есть, но не задокументирована публично, либо её ещё нет в описанном виде. **[проверено, что в доступной документации по адресу dev.max.ru/docs-api эта тема отсутствует; это не доказательство отсутствия фичи, а честная фиксация «в официальных доках не нашли»]**
- Есть неофициальная reverse-engineered документация протокола (github.com/pr0bel1230/max-api-docs), не покрывающая тему og-tags в найденных фрагментах.
- **Вывод: для MAX в 2026 нет публично подтверждённого канона по превью ссылок.** Разумная защитная стратегия для шаблона — просто отдавать полный набор `og:*` (title/description/image с абсолютным URL) на всякий случай, поскольку большинство мессенджеров-клонов (основанных на типовых webview/Telegram-подобных архитектурах) в индустрии по умолчанию парсят OG до появления собственной специфики. Это **предположение**, не факт.

**Рекомендация для `ssr-frontend-template` (Node 24 Alpine, без CDN):**

Пайплайн **satori → @resvg/resvg-js → (опционально sharp)**:
1. Собрать JSX-разметку карточки (заголовок, подзаголовок, лого) → `satori(jsx, { width: 1200, height: 630, fonts: [{ name: 'Inter', data: interCyrillicBuffer, weight: 600, style: 'normal' }] })` → строка SVG.
2. `new Resvg(svgString, { fitTo: { mode: 'width', value: 1200 } }).render().asPng()` → Buffer PNG.
3. При необходимости — `sharp(pngBuffer).webp({ quality: 82 })` для дополнительного формата/сжатия (если хочется отдавать `image/webp` части клиентов).

Обоснование выбора именно этой связки, а не `@vercel/og`: `@vercel/og` — это тонкая обёртка ровно над тем же satori+resvg (только resvg через WASM), так что использование связки напрямую даёт **контроль над кешированием и заголовками ответа** (что нужно для non-Vercel деплоя) и на один слой абстракции меньше; при этом сам `@vercel/og` тоже валиден как быстрый старт, если не хочется писать обвязку самому — и WASM-вариант resvg внутри него даже безопаснее с точки зрения musl-совместимости (WASM не зависит от target triple вообще).

Headless-browser (playwright/puppeteer) — **не рекомендуется** для этой задачи: несовместимость Alpine у Playwright официально задокументирована, а puppeteer на Alpine — это неофициальный, тяжёлый (300+MB) путь ради результата, который проще и быстрее получить через satori.

**Кириллица** — критично не забыть подключить шрифт с кириллическими глифами (Inter, Noto Sans, PT Sans и т.п.) как файл в самом Docker-образе (не полагаться на системные шрифты — на Alpine их обычно вообще нет, и satori их не использует принципиально). Для смешанного ru/en сайта достаточно одного шрифта с обоими наборами глифов.

**Кеширование сгенерированных OG-картинок:**
- `@vercel/og` в проде по умолчанию отдаёт `Cache-Control: public, immutable, no-transform, max-age=31536000` **[вторично: сообщество + доки vercel.com/docs/og-image-generation]** — паттерн стоит скопировать.
- Рекомендуемая стратегия для SSR без CDN: кешировать по ключу `slug+lang+contentHash` (не просто по URL страницы) — генерировать один раз на диск (или in-memory LRU) при первом запросе, отдавать `ETag` = хэш этого ключа (например, sha256 первых 16 hex), поддерживать `If-None-Match` → `304 Not Modified`. Инвалидация — через смену хэша в URL картинки при изменении контента (контент-адресация), а не через явный purge — тогда безопасно ставить `immutable`.
- Если картинка встраивается по стабильному URL `/og/[slug].png` без хэша — тогда `immutable` ставить нельзя, нужен короткий `max-age` + `stale-while-revalidate`, либо принудительная ре-генерация при деплое.

### A.6 favicon / manifest / theme-color

**Минимальный набор в 2026** **[частично проверено: evilmartians.com/chronicles/how-to-favicon-in-2021-six-files-that-fit-most-needs (актуализируется под текущий год — заголовок статьи в найденной выдаче показывает «How to Favicon in 2026»); частично MDN]**:

1. `favicon.ico` (мультиразмерный 16/32/48, либо просто 32×32) — legacy-фолбэк для тех, кто не смотрит `<link>` вообще (некоторые боты, старые агенты берут `/favicon.ico` по конвенции пути даже без тега).
2. `icon.svg` — основной современный favicon, масштабируемый; может содержать **`@media (prefers-color-scheme: dark)`** прямо внутри самого SVG (через `<style>`), чтобы одна иконка переключалась под системную тему без дублирования файлов.
3. `apple-touch-icon.png`, **180×180** — обязателен отдельно, т.к. iOS/iPadOS не используют обычный favicon для «Добавить на экран Домой», без него показывается непривлекательный скриншот страницы. **[проверено: developer.mozilla.org — Define app icons/иконки PWA раздел про apple-touch-icon]**
4. `manifest.webmanifest` — со ссылкой `<link rel="manifest">`; внутри — иконки для PWA/Android home screen.

**Про manifest-иконки — важное уточнение, где я поправил вторичные источники:**
Несколько SEO/favicon-блогов 2026 года утверждают, что «Android требует растр, SVG в manifest не работает». Официальная MDN-документация это **не подтверждает** — прямо разрешает `"sizes": "any", "type": "image/svg+xml"` в массиве `icons` манифеста. **[проверено: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/icons]** Практическая рекомендация всё равно — держать PNG 192×192 и 512×512 (в т.ч. один с `"purpose": "maskable"`) как гарантированно совместимый путь, а SVG с `sizes: "any"` добавлять дополнительно, не вместо. Ни 192, ни 512 не являются жёстко обязательными по спецификации — это устоявшаяся конвенция экосистемы (Chrome предлагает установку PWA, ориентируясь на них), а не заданное число в стандарте.

**theme-color:**
```html
<meta name="theme-color" content="#ffffff" media="(prefers-color-scheme: light)">
<meta name="theme-color" content="#0a0a0a" media="(prefers-color-scheme: dark)">
```
Поддержка `media`-атрибута в связке с `prefers-color-scheme` — Safari с версии 15 (macOS/iOS), Chrome/Brave/Samsung Internet на Android, инсталлированные PWA в Chrome/Safari. **[проверено: developer.mozilla.org/.../meta/name/theme-color, через WebSearch-сниппет с точным текстом MDN]** Firefox desktop исторически `theme-color` вообще игнорирует (это про UI мобильного браузера/PWA, не про desktop chrome).

**`<meta name="color-scheme">`:**
```html
<meta name="color-scheme" content="light dark">
```
Значение `light dark` — сайт поддерживает оба, приоритет — первому в списке. Смысл — не просто эстетика, а тайминг: этот тег в `<head>` до CSS позволяет **браузеру сразу отрисовать нативные виджеты формы/скроллбар/фон в нужной схеме до применения авторского CSS**, устраняя white-flash при первой отрисовке в dark mode. Поддержка: Chrome/Edge 81+, Firefox 96+, Safari 13+. **[проверено: web.dev/articles/color-scheme]** Для SSR это особенно важно: значение темы должно быть известно на сервере до рендера `<head>` (например, из cookie), а `color-scheme` — простой быстрый способ подсказать браузеру ещё до гидратации.

### A.7 `<html lang>` при SSR

- `lang` — ISO-код языка (`ru`, `en`, при необходимости региональный вариант `en-GB`); должен **точно совпадать с фактическим языком контента страницы**, а не быть захардкожен в шаблоне вне зависимости от роута — иначе Google может отнести страницу не в тот языковой пул выдачи, а скринридеры выберут неверные правила произношения/переноса. **[вторично, но общепринято и логично из первых принципов a11y/WCAG]**
- При SSR это означает: значение `lang` для корневого `<html>` должно резолвиться **на сервере** из сегмента маршрута/локали до первого байта HTML (а не выставляться через `useEffect` на клиенте — тогда краулер и screen reader первого прохода увидят дефолт/пустоту). Для TanStack Start это конкретно значит выставлять `lang` через `head()`/root document shell на основе loader/route context, а не постфактум в браузере.
- `dir` — нужен только если в проекте появляется RTL-язык (арабский, иврит и т.п.); для ru/en не требуется, но сам хелпер стоит спроектировать с полем `dir` на будущее (`dir="ltr"` по умолчанию), а не хардкодить его отсутствие.
- Каждый язык страницы также должен иметь `hreflang`-альтернативы (`<link rel="alternate" hreflang="ru" href="...">`, плюс `x-default`) — формально это не тема `<html lang>`, но тот же слой SSR-хелпера логично отвечает за оба одновременно, т.к. данные (список локалей страницы) общие.

### B.9 Где размещать JSON-LD

**[проверено: https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data]**

- Google принимает `<script type="application/ld+json">` **и в `<head>`, и в `<body>`** — дословно: *«A JavaScript notation embedded in a `<script>` tag in the `<head>` and `<body>` elements of an HTML page»*. Для FSD-архитектуры проекта это значит: JSON-LD можно генерировать прямо там, где по слоям удобнее (например, widget/page сам добавляет свой блок через `head()`), не обязательно поднимать всё в один корневой `app`-компонент.
- **Динамически инжектированный через JS JSON-LD Google явно поддерживает**: *«Google can read JSON-LD data when it is dynamically injected into the page's contents, such as by JavaScript code or embedded widgets»* — то есть для SSR это тем более не проблема: контент есть в HTML с первого байта, а не только «после гидратации», что даже надёжнее, чем чисто клиентская инъекция, о которой и так явно сказано, что Google её читает.
- **Несколько `<script>`-блоков и `@graph`** — прямого официального указания «можно» или «нельзя» в policy-документе не встретилось, но это давно устоявшаяся, широко задокументированная в схеме.org и повсеместно используемая (в т.ч. самим Google в собственных примерах для сложных страниц) практика: несколько независимых `<script type="application/ld+json">` блоков **или** один блок с массивом через `@graph` — оба варианта одинаково валидны, выбор — вопрос удобства кодогенерации. **[предположение в части «Google это явно прописал» — не нашёл прямой цитаты; сам факт поддержки — общеизвестный и подтверждается валидаторами schema.org/Rich Results Test, которые штатно понимают оба паттерна]**
- **CSP nonce для `application/ld+json` не требуется.** Технически: директива `script-src` регулирует **исполнение** скриптов; `<script type="application/ld+json">` браузер не исполняет как JavaScript (это «data block» по HTML-спеке), поэтому он не подпадает под ограничения `script-src`, и добавлять туда `nonce` — избыточно (в комьюнити прямо называют это «cargo culting»). Официальная страница MDN про `script-src` этот конкретный кейс не разбирает явно (нашлось только явное упоминание, что `script-src` покрывает `<script type="speculationrules">` отдельной оговоркой) — то есть вывод подтверждён логикой спецификации + практикой (примеры структурированных данных от Google никогда не показывают nonce), но не отдельной явной строкой в тексте MDN. **[проверено частично: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src — общий принцип «script-src регулирует JS execution» подтверждён; конкретное исключение для ld+json — вторично через практику и объяснения комьюнити]**. Практическая рекомендация для проекта: **не заводить nonce-инфраструктуру ради JSON-LD**; nonce нужен только реальным исполняемым `<script>` (аналитика и т.п.), если они появятся.
- Общие качественные требования Google к разметке (не про размещение, но важно для генератора): контент разметки должен **соответствовать видимому контенту страницы** (нельзя описывать то, чего нет на странице), нельзя размечать поддельные отзывы/нерелевантный контент, и страница со структурированными данными не должна блокироваться от Googlebot через robots.txt/noindex. **[проверено: https://developers.google.com/search/docs/appearance/structured-data/sd-policies (через сниппет), одноимённая доктрина]**

### B.11 Типобезопасный JSON-LD в TypeScript

**`schema-dts`** (`google/schema-dts`, официально не Google-продукт — *«This is not an officially supported Google product»*, но поддерживается активно) **[проверено: registry.npmjs.org/schema-dts/latest → версия 2.0.0; github.com/google/schema-dts, pushed_at 2026-09-01 — активная разработка на дату исследования]**:

```bash
pnpm add -D schema-dts
```

```ts
import type { Organization, WithContext } from 'schema-dts'

const organizationJsonLd: WithContext<Organization> = {
  '@context': 'https://schema.org',
  '@type': 'Organization',
  name: 'Acme',
  url: 'https://acme.example',
}
```

- `WithContext<T>` — добавляет `@context`/`@type` к «голому» интерфейсу типа `Organization`/`Product`/`Article` и т.д.
- Для случаев, где TS union по `@type` мешает (например, при реализации через `class`), пакет предоставляет «leaf»-интерфейсы (`PersonLeaf` и т.п.) без дискриминирующего union.
- Типы генерируются из актуального словаря schema.org — то есть версия пакета фактически привязана к версии словаря на момент релиза; при мажорном обновлении schema.org может понадобиться апдейт пакета.

**Альтернативы:**
- Писать литералы `as const satisfies Record<string, unknown>` вручную без пакета — ноль зависимостей, но нет автодополнения/проверки обязательных полей.
- `zod`-схемы под конкретные типы JSON-LD, которые уже используются в проекте для контрактов API (`entities/<name>/model/schema.ts`) — тяжелее в поддержке (нужно самим гнаться за словарём schema.org), но даёт **runtime**-валидацию (а не только compile-time, как `schema-dts`) — что может быть ценно именно для теста «сгенерированный JSON-LD синтаксически и структурно корректен» в CI (см. B.10 про замену заброшенного `structured-data-testing-tool`).
- Практическая рекомендация для этого шаблона: `schema-dts` для compile-time типов в хелперах `shared/seo`, plus тонкий unit-тест (Vitest), который на каждый сгенерированный объект проверяет `JSON.parse(JSON.stringify(x))` не бросает, обязательные поля (`@context`, `@type`, `name`/`url` и т.п. — по минимальному подмножеству, которое реально использует проект) присутствуют — не пытаясь заново реализовать «валидатор schema.org», а просто gate на регресс.

## Итоговые рекомендации по коду (`shared/seo`)

1. Один хелпер `buildPageMeta({ title, description, image, locale, alternateLocales, path })`, который одновременно возвращает: `<title>`, `og:*`, `twitter:*`, `hreflang`-links — потому что источник данных (заголовок/описание/картинка/список локалей) один и тот же, разносить логику по трём независимым хелперам — источник рассинхронизации (напр. title и og:title разъедутся).
2. Отдельный хелпер/эндпоинт `/og/[...].png` — Node route handler (не React-компонент), пайплайн satori → resvg → (опц.) sharp, с кешированием по контент-хэшу и `Cache-Control: public, immutable, max-age=31536000` для хэшированных URL.
3. Отдельный модуль `shared/seo/jsonld.ts` на `schema-dts`: чистые билдер-функции `organizationJsonLd()`, `websiteJsonLd()`, `breadcrumbJsonLd(items)` и т.д., рендерящиеся в `<script type="application/ld+json">` без nonce.
4. Тест на уровне Vitest: снапшот/структурная проверка, что каждый билдер даёт валидный JSON (парсится, обязательные поля на месте) — без внешней зависимости на заброшенный `structured-data-testing-tool`.
5. `lang`/`dir`/`theme-color`/`color-scheme` — в корневом document shell (не per-page), резолвятся на сервере из route/locale/theme-cookie контекста до рендера.

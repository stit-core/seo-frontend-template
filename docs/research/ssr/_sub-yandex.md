## 1. Индексирование JS у Яндекса

**Источник:** https://yandex.ru/support/webmaster/ru/yandex-indexing/rendering — **проверено (fetched напрямую, 2026-09-15)**

- Функция называется «Рендеринг страниц JavaScript» и официально помечена как **бета (β)**. Статус беты сохраняется по состоянию на сентябрь 2026 — специального объявления о выходе из беты не найдено.
- Управляется в Вебмастере: **Индексирование → Рендеринг страниц JavaScript**.
- Назначение: управлять, будет ли робот Яндекса выполнять JavaScript при обходе страниц — актуально для сайтов **без SSR/пререндеринга**.
- Режим по умолчанию — **«На усмотрение робота Яндекса»**: робот сам решает, выполнять ли JS, оценивая качество и полноту полученного контента. Полный список остальных вариантов переключателя (например, «всегда»/«никогда») в документации явно не перечислен — страница описывает только дефолтный режим и явную рекомендацию **выключить** рендеринг, если на сайте уже есть SSR/пререндеринг. Это единственная официальная формулировка, других значений enum достоверно найти не удалось → **пробел в документации Яндекса**, а не пропуск в исследовании.
- Явно указанное ограничение: *«При выполнении JavaScript-кода робот может создавать дополнительную нагрузку на ваш сервер»*.
- Рядом существует смежная бета-функция **«Проверка страницы»** (page inspection) — упомянута в блоге как парная фича: webmaster.yandex.ru/blog/rendering-stranits-javascript-i-proverka-stranitsy-peredavayte-poisku-kontent-v-polnom-obeme — **проверено**.

### window.YandexRotorSetting

Создаётся на страницах с отложенной (после `DOMContentLoaded`) загрузкой контента. Полный набор полей, найденный в документации:

| Поле | Тип | Семантика |
|---|---|---|
| `WaiterEnabled` | Boolean | Включает саму проверку состояний `IsLoaded`/`IsError` (без него объект не активен) |
| `IsLoaded` | Boolean или функция | `true` — контент уже загружен после `DOMContentLoaded`; можно передать функцию, которая сама вычисляет готовность (например, проверяет наличие DOM-узлов) |
| `IsError` | Boolean | `true` — загрузка завершилась ошибкой, контент не обрабатывается роботом |
| `FailOnTimeout` | Boolean | `true` — при превышении тайм-аута ожидания страница не индексируется вовсе; `false` — индексируется то, что успело загрузиться (частичная индексация) |
| `NoJsRedirectsToMain` | Boolean | `true` — робот игнорирует JS-редирект на главную страницу (типичный паттерн SPA с History API), чтобы не подменить индексируемый контент главной страницей |

Источник тот же (rendering.html). Это **самая полная выжимка из официальной страницы** — независимых источников с большим числом полей не нашлось; WebSearch по `window.YandexRotorSetting` не дал сторонних доков (только сама страница Яндекса и нерелевантные результаты про рендеринг в других системах).

### Рекомендация для шаблона

Явная официальная позиция: *«Запретите рендеринг, если реализованы SSR или пререндеринг»*. Поскольку шаблон — TanStack Start с полноценным SSR, для прод-конфигурации логично **явно выключать** JS-рендеринг Яндекса в Вебмастере (а не полагаться на дефолтный «на усмотрение робота»), плюс полагаться на ожидание конкретных DOM-элементов, а не фиксированные задержки, если где-то всё же остаётся клиентская гидратация с отложенным контентом.

## 2. robots.txt у Яндекса

**Основной источник (актуальная страница, лежит на новом URL-паттерне `/controlling-robot/`):**
https://yandex.ru/support/webmaster/ru/controlling-robot/robots-txt — **проверено (fetched напрямую)**

### Поддерживаемые директивы (2026)

| Директива | Статус | Комментарий |
|---|---|---|
| `User-agent` | Поддерживается, обязательна | Строки, начинающиеся с `User-agent:`, ищутся с подстрокой `Yandex` (без учёта регистра) или `*` |
| `Disallow` | Поддерживается | Запрет обхода |
| `Allow` | Поддерживается | Явное разрешение, приоритет разрешает конфликт по длине правила |
| `Sitemap` | Поддерживается | Путь к sitemap-файлу |
| `Clean-param` | Поддерживается, **Яндекс-специфична** | См. п.3 |
| `Crawl-delay` | **Официально не учитывается** | См. ниже |
| `Host` | **Официально отменена** | См. ниже |

**Host** — отменена **12 марта 2018** (пост Платона Щукина, штатного сотрудника Яндекса): https://yandex.ru/blog/platon/pereezd-sayta-posle-otkaza-ot-direktivy-host — **проверено**. Причина: директива требовала синхронной проверки «одинаковости» адресов на всех зеркалах, что было неудобно и не масштабировалось. Вместо неё — **HTTP 301-редирект** с формальной заявкой на переезд сайта через Вебмастер. Директиву можно оставить в файле (робот её просто проигнорирует) или удалить — на индексирование не влияет.

**Crawl-delay** — вторичные источники (searchengines.guru, seo.ru) сходятся: Яндекс перестал учитывать эту директиву, так как некорректно выставленные значения были частой причиной медленной закачки документов. Официальной страницы, прямо констатирующей отмену, найти через основной robots.txt-документ не удалось (страница про сам robots.txt её просто не упоминает вовсе — что тоже показательно). Вместо неё — инструмент **«Скорость обхода»** в Вебмастере: **Индексирование → Скорость обхода**, https://yandex.ru/support/webmaster/ru/service/crawl-rate — **проверено (fetched напрямую)**. Режимы: «Доверять Яндексу» (автоматический расчёт оптимальной скорости) и «Задать вручную» (ползунок, заданное значение — «рекомендация» для робота, а не жёсткий лимит). Итог: считать Crawl-delay **устаревшей/недействующей** директивой, в шаблон не закладывать, при необходимости ограничить скорость обхода — управлять через Вебмастер (не файлово, значит это не про env/robots.txt-генерацию в SSR-шаблоне).

### Приоритет директив и спецсимволы

- `*` и `$` поддерживаются в `Allow`/`Disallow` начиная с «расширенного формата robots.txt», анонсированного Яндексом **21 декабря 2007** (пост Александра Садовского): https://webmaster.yandex.ru/blog/14 — **проверено**. `*` — подстановка любой последовательности символов (в т.ч. пустой); по умолчанию каждое правило неявно заканчивается на `*`, если явно не поставлен `$`. `$` — отменяет неявный `*` в конце строки, но не отменяет `*`, поставленный явно.
- Приоритет при пересечении `Allow`/`Disallow`: побеждает правило с **большей длиной строки** совпадения (а не порядок следования в файле).
- Пустая директива `Allow:` — с **10 июня 2016** трактуется как **игнорируемая** (раньше воспринималась как полный запрет индексирования — частая ошибка новичков): https://webmaster.yandex.ru/blog/izmeneniya-v-obrabotke-robots-txt — **проверено**. Для полного запрета нужно `Disallow: /`.

### Требования к файлу

Источник — основная страница robots-txt (см. выше), **проверено**:
- Максимальный размер — **500 КБ**.
- Имя файла строго `robots.txt` (в нижнем регистре), корневой каталог сайта.
- Кодировка — только UTF-8; **кириллица в самом файле запрещена** — для доменов нужен Punycode, для путей — соответствующая кодировка сайта (percent-encoding).
- Сервер должен отвечать **200 OK** на запрос robots.txt (либо редиректом на другой robots.txt с итоговым 200).
- Если файл не соответствует требованиям (недоступен, отдаёт ошибку, превышает размер и т.п.) — **«сайт считается открытым для индексирования»**, т.е. отсутствие корректного robots.txt = разрешение всё индексировать, а не запрет.

### Трактовка 4xx/5xx

Отдельно проверено через блог-пост «Нет доступа: код ответа 4ХХ» (5 сентября 2022): https://webmaster.yandex.ru/blog/net-dostupa-kod-otveta-4khkh — **проверено**. В комментариях штатный сотрудник (аккаунт platon) прямо отвечает: *«Файлы robots.txt и Sitemap не участвуют в поиске»* — их 4xx/5xx-статус **не влияет на индексирование сайта** сам по себе, за исключением того, что определяет, применяются ли директивы файла:
- **4xx на сам robots.txt** (включая 404/410) → трактуется как «файла нет» → сайт полностью открыт для обхода (директивы не действуют).
- **5xx на сам robots.txt** → по консолидированным вторичным источникам робот временно приостанавливает/откладывает обход до восстановления доступа (аналогично общей практике поисковиков), но прямой действующей формулировки именно от Яндекса на этот счёт (в отличие от 4xx) найти не удалось — помечаю как **предположение по аналогии**, не как жёстко подтверждённый факт.
- Важно не путать с 4xx на **обычных страницах сайта** (не сам robots.txt) — это отдельная история («страница пропадёт из индекса»), не связанная с обработкой robots.txt.

### User-agent токены

https://yandex.ru/support/webmaster/ru/robot-workings/user-agent.html — **проверено**. Иерархия: если есть блок `User-agent: Yandex`, блок `User-agent: *` для Яндекса игнорируется целиком; если есть блок для конкретного специализированного робота (пример в документе — `YandexBot`), то игнорируются уже оба — и `User-agent: Yandex`, и `User-agent: *`. Полный перечень специализированных токенов (YandexImages, YandexMedia, YandexDirect и т.п.) на этой странице **не приведён исчерпывающе** — упомянут лишь `YandexBot` как пример основного индексирующего робота. Для целей шаблона это не критично: обычно достаточно одного блока `User-agent: Yandex` (или `*`).

## 3. Clean-param

**Источник:** https://yandex.ru/support/webmaster/ru/robot-workings/clean-param — **проверено (fetched напрямую)**

### Синтаксис

```
Clean-param: p0[&p1&p2&...&pn] [path]
```
- Первое поле — параметры через `&`, которые не влияют на содержимое страницы и должны игнорироваться роботом.
- Второе поле (опционально) — префикс пути, к которому применяется правило; без него действует по всему сайту.
- Директива **межсекционная** — валидна в любом месте файла robots.txt, привязывать её к `User-agent: Yandex` не обязательно.

Примеры из документации:
```
User-agent: Yandex
Clean-param: ref /some_dir/get_book.pl
Clean-param: s&ref /forum*/showthread.php
Clean-param: utm
```

### Лимиты

- Ограничение длины **одного правила — 500 символов** (сам URL после подстановки параметров не должен превышать это ограничение внутри robots.txt).
- Максимальное число параметров в одной директиве явно не оговорено — практическое ограничение задаётся лимитом в 500 символов на строку.

### Автоматически отбрасываемые параметры

Яндекс автоматически распознаёт и «схлопывает» без Clean-param:
- `ysclid`, `yrclid` (Яндекс-метки кликов)
- `utm_source`, `utm_medium`, `utm_term`, `utm_content`, `utm_campaign`, `utm_media`, `utm_group`, `utm_expid`, `utm_referrer`

Для этих параметров дополнительных действий в robots.txt не требуется — Яндекс обрабатывает их сам. **`gclid`, `yclid` (устаревшее название `ysclid`), `_openstat`** отдельно в зафетченном тексте не упомянуты — по не-первоисточникам встречается упоминание, что похожие клик-ID параметры конкурентов Яндекс не гарантирует, что распознаёт автоматически → безопаснее закладывать явный `Clean-param` для нестандартных трекинг-параметров, специфичных для проекта.

### Соотношение с другими механизмами

- **Приоритет Disallow выше**: если страница закрыта `Disallow`, `Clean-param` её не «спасёт» и не переопределит запрет.
- **Соотношение с rel=canonical**: прямой связи в тексте самой страницы Clean-param нет, но на странице про canonical (см. п.6) Яндекс прямо рекомендует: *«Для исключения параметровых URL используйте директиву Clean-param в robots.txt»* — то есть Clean-param это предпочтительный Яндексом инструмент именно для параметров трекинга/сессий, а rel=canonical — более общий механизм на уровне контента страницы (дубли, а не служебные параметры).

## 4. Тег `<noindex>` / `<!--noindex-->`

**Источники:** https://yandex.ru/support/webmaster/ru/robot-workings/vision — **проверено**; https://yandex.ru/support/webmaster/ru/adding-site/indexing-prohibition — упомянута, содержимое частично.

- Тег **`<noindex>текст</noindex>`** — Яндекс-специфичное расширение (не стандарт HTML), поддерживается в 2026 году для скрытия **фрагмента** текста от индексации (в отличие от `Disallow`/`meta robots noindex`, которые скрывают всю страницу).
- Официальная формулировка: *«Если вы хотите скрыть только часть содержимого страницы, используйте теги `noindex` или `noscript»`* — то есть Яндекс сам ставит их через запятую как взаимозаменяемые варианты для этой цели на странице vision.
- Ключевое поведение (со страницы о видимости/скрытии): элемент **не блокирует переход робота по ссылкам внутри** скрытого фрагмента — блокируется только индексация текста, не обход ссылок.
- **Не чувствителен к вложенности** — можно ставить в любом месте HTML.
- Если отсутствует закрывающий тег — **всё содержимое страницы от места открывающего тега и до конца считается скрытым**.
- Явное предупреждение Яндекса: **не путать** этот элемент с одноимённой директивой `noindex` в `meta name="robots"` — семантика разная (там — вся страница целиком, здесь — фрагмент).
- **Что не удалось подтвердить первоисточником**: явной свежей (2025–2026) официальной страницы/поста, отдельно подтверждающей продолжение поддержки именно в 2026 году, не нашлось — страница vision не датирована explicitly и не содержит форвард-only оговорок об изменениях. Вторичные источники (адлук, rush-analytics и т.д., не первоисточники) массово подтверждают актуальность в 2026 году, но это агрегаторы, не сам Яндекс.
- **rel=nofollow vs noindex — «что изменилось»**: однозначного официального пресс-релиза Яндекса 2022–2023 гг. про изменение трактовки `rel=nofollow` (передача/непередача веса) через первоисточник найти не удалось — WebSearch дал только общую информацию о механике nofollow и о том, что Google вводил `sponsored`/`ugc`, но не нашёл датированного официального заявления Яндекса на этот счёт → **помечаю как неподтверждённое / вероятно относится к периоду до 2026 и не задокументировано в открытых источниках Яндекса на русском языке в найденном объёме**. Практическая рекомендация индустрии (не первоисточник): использовать `rel="nofollow"` (можно вместе с `ugc`/`sponsored` для совместимости с Google) — Яндекс новые значения `sponsored`/`ugc` отдельно **не документирует** как значимые для себя.

## 5. meta robots и X-Robots-Tag у Яндекса

**Источники:** https://yandex.ru/support/webmaster/ru/controlling-robot/meta-robots (RU) и https://yandex.com/support/webmaster/en/controlling-robot/meta-robots.html (EN) — **проверено обе, содержимое идентично по составу директив**.

### Поддерживаемые директивы

| Директива | Тип | Значение |
|---|---|---|
| `noindex` | запрещающая | не индексировать текст страницы, страница не попадёт в выдачу |
| `nofollow` | запрещающая | не переходить по ссылкам на странице |
| `none` | запрещающая | эквивалент `noindex` + `nofollow` одновременно |
| `noarchive` | запрещающая | не показывать ссылку на сохранённую копию в выдаче |
| `index`, `follow`, `archive` | разрешающая | явно отменяют соответствующие запрещающие |
| `all` | разрешающая | эквивалент `index` + `follow` |

**Явно НЕ подтверждены как поддерживаемые** (отсутствуют в обеих версиях официальной страницы — и RU, и EN): `nosnippet`, `max-snippet`, `notranslate`, `noimageindex`, `unavailable_after`, `max-image-preview`, `max-video-preview`, `indexifembedded`. Это Google-специфичные директивы. Отдельным WebSearch по формулировке «Яндекс не поддерживает nosnippet/max-snippet» подтверждено несколькими независимыми SEO-источниками (не первоисточник, но консистентно) — трактую как **достаточно надёжный вывод от противного**: страница-перечисление у Яндекса исчерпывающая (даёт таблицу «запрещающие/разрешающие» без оговорки «и другие»), и независимые источники прямо констатируют отсутствие поддержки.

### X-Robots-Tag

Официально поддерживается: *«настройка через HTTP-заголовок X-Robots-Tag для определённого URL на сервере вашего сайта»*, при этом **все директивы, работающие в мета-теге, работают и в заголовке** (набор директив тот же, что в таблице выше). Пример из документации:
```
X-Robots-Tag: noindex, nofollow
X-Robots-Tag: noarchive
```
Можно указывать несколько заголовков в одном ответе или перечислять через запятую в одном заголовке.

### User-agent токен Яндекса

Специфичный токен — не HTTP User-Agent, а **атрибут `name` меta-тега**: `<meta name="yandex" content="noindex"/>` — таргетирует директиву только на робота Яндекса (аналогично `<meta name="googlebot">` у Google). Если на странице одновременно стоят общий `<meta name="robots">` и специфичный `<meta name="yandex">`, **обе директивы учитываются** роботом Яндекса.

### Конфликт директив

Официальная формулировка: *«Разрешающие директивы имеют приоритет в сочетании с запрещающими»* — то есть при противоречии (`noindex` + `index` одновременно) побеждает **разрешающая**.

## 6. rel=canonical у Яндекса

**Источник:** https://yandex.ru/support/webmaster/ru/robot-workings/canonical — **проверено (fetched напрямую)**

- Поддерживаются **два способа** указания:
  1. HTML: `<link rel="canonical" href="http://www.example.com/blog"/>`
  2. HTTP-заголовок **Link**: `Link: <http://www.example.com/offer/file.pdf>; rel="canonical"` — то есть canonical через HTTP-заголовок **официально поддерживается**, что удобно для генерации на сервере (актуально для SSR-шаблона — не обязательно всегда рендерить `<link>` в `<head>`, можно отдавать заголовком).
- **Cross-domain canonical НЕ поддерживается**: если каноническим указан URL на другом домене/поддомене — робот это указание проигнорирует.
- **Конфликтные ситуации**, которые робот игнорирует:
  - Указано **несколько** канонических адресов на одной странице.
  - **Цепочка** canonical (A→B, но у B указан canonical→C) — не поддерживается, робот не «схлопывает» цепочку.
  - Canonical ведёт на закрытую от индексирования или редиректящую куда-то ещё страницу — игнорируется.
- Robot воспринимает canonical как **рекомендацию, а не директиву** — может проигнорировать, если содержимое целевой и текущей страницы существенно различается, либо если «неканоническая» страница по факту лучше отвечает на запросы пользователей.
- Официальные рекомендации Яндекса:
  - Использовать **абсолютные** пути.
  - При переезде HTTP→HTTPS использовать **301/302 редирект**, а не canonical (для такого сценария canonical признан неподходящим инструментом).
  - Для параметризованных URL (трекинг, сессии, сортировки и т.п.) — использовать **Clean-param**, а не canonical.

## 7. hreflang у Яндекса

**Источник:** https://webmaster.yandex.ru/blog/15326 (редирект с yandex.ru/blog/webmaster/15326), дата — **9 апреля 2013** — **проверено, но источник старый**.

- Яндекс поддерживает стандартный атрибут **`rel="alternate" hreflang="x"`**:
```html
<link rel="alternate" hreflang="en-us" href="http://example.com/en-us/">
<link rel="alternate" hreflang="ru-ru" href="http://example.com/ru-ru/">
```
- Каждая языковая версия должна содержать ссылки на **все** остальные версии (включая self-reference на саму себя).
- **x-default** — официально поддерживается, причём именно как результат согласованного шага Яндекса и Google: страница-fallback для пользователей, для которых нет явной региональной/языковой версии (например, определяется по IP или через селектор языка на сайте).
- Официальная формулировка статуса: hreflang — **«не директива, а рекомендация»** для поисковика, он сам решает, использовать ли её.
- **Важная оговорка для 2026 года**: первоисточник от 2013 года — это единственный найденный официальный документ Яндекса именно про hreflang; более свежих официальных страниц с тем же содержанием (например, в актуальном `/support/webmaster/` дереве) через WebSearch обнаружить не удалось — вероятно, тема просто «влилась» в общий блок региональности и отдельной актуализированной страницы под hreflang в текущей структуре доков нет. Косвенно это подтверждается независимыми источниками 2024–2025: Яндекс **в первую очередь опирается на региональные настройки в Вебмастере** (см. п.8), а hreflang — вспомогательный сигнал, причём разработчики отмечают случаи, когда Яндекс **на практике игнорирует** hreflang на двуязычных сайтах (форумное наблюдение, не первоисточник, но многократно повторяется).
- **Рекомендация для ru/en-шаблона**: закладывать hreflang (`ru`, `en`, `x-default`) как гигиенический стандарт (не вредит, поддерживается Google полноценно), но **не полагаться на него как на единственный сигнал языковой/региональной принадлежности для Яндекса** — обязательно дублировать регион через настройки Вебмастера (п.8) и через понятную языковую структуру URL (например, `/ru/`, `/en/` в путях, а не только hreflang в `<head>`).

## 8. Региональность

**Источники:** https://webmaster.yandex.ru/blog/13134 («Региональность сайта: практические рекомендации»), https://webmaster.yandex.ru/blog/regionalnost-voprosy-i-otvety — оба через WebSearch-выжимку, **не fetch-нуты напрямую целиком**, доверие среднее-высокое (это блог самого Яндекса, но контент получен через сниппет поиска, а не прямым fetch).

- Региональность важна для геозависимых запросов (`такси`, `купить айфон` и т.п.) — пользователь ожидает результаты из своего региона.
- Настройка — в Вебмастере: **«Информация о сайте» → «Региональность»** → «Добавить регион» → указать населённый пункт.
- Для мультирегиональных сайтов (несколько городов) — можно задать основной регион плюс добавить дополнительные точки через справочник (Яндекс.Бизнес/Карты), привязанные к тому же сайту; после проверки сайт начинает ранжироваться сразу в нескольких регионах.
- **Роль домена**: зона `.ru` (а также `.su`, `.рф`) по умолчанию трактуется Яндексом как принадлежность к русскоязычному и российскому сегменту — такие сайты, по консолидированным данным, обычно индексируются/ранжируются в регионах RU **чуть быстрее/охотнее**, чем `.com` и другие зоны, но это не хардкодированное правило ранжирования, а сигнал по умолчанию. Сайт на `.com` **не будет ранжироваться хуже**, если контент релевантен и явно ориентирован на русскоязычную аудиторию — донастройка региональности через Вебмастер компенсирует «нейтральность» домена.
- Для контента вне явной геопривязки (что типично для SPA/SaaS-шаблона) рекомендация — насыщать контент региональными сигналами (адреса, упоминания городов и т.п.), чтобы робот мог **автоматически** определить региональность, если она не выставлена вручную.
- **Что не удалось подтвердить первоисточником напрямую**: точный актуальный (2026) URL страницы «Региональность сайта» в дереве `/support/webmaster/` (нашёлся только устаревший `yandex.ru/support/webmaster/search-results/site-region.xml`, который выглядит как старый путь) — не фетчился напрямую, содержание синтезировано из сниппетов блога.

## 9. Структурированные данные у Яндекса

**Основные источники:**
- https://yandex.ru/support/webmaster/ru/schema-org/what-is-schema-org — **проверено (fetched)**
- https://yandex.ru/support/webmaster/ru/schema-org/semantic-faq.html — **проверено (fetched)**
- https://yandex.ru/support/webmaster/ru/json-ld/about.html — **проверено (fetched)**
- https://yandex.ru/support/webmaster/ru/supported-schemas/navigation-links (breadcrumbs) — **проверено (fetched)**
- Раздел `supported-schemas/*` в целом обнаружен через site-search: address-organization.html, movie-description.html, q-and-a.html, catalogs — **найдены через WebSearch, не все fetch-нуты индивидуально**.

### Поддерживаемые форматы

- **Microdata** — полностью поддерживается, названа «самым популярным форматом микроразметки в рунете» (вторичный источник) — но и первоисточник (semantic-faq) прямо упоминает микроформаты (hProduct и т.п.) и Schema.org как основу.
- **JSON-LD** — официально поддерживается, отдельная документация (`/json-ld/about.html`): данные размещаются в теге `<script>`, все ключи/значения **регистрозависимы** (`@context`, `@type` и т.п. — точное написание обязательно). Используется, в частности, для хлебных крошек и Q&A.
- **Open Graph** — поддерживается (упомянут в перечне валидатора).
- **RDFa** — поддерживается (в перечне валидатора; также подтверждено историческими постами Яндекса на W3C public-vocabs листах от сотрудников yandex-team.ru).
- Официальная позиция: *«Наши алгоритмы не отдают предпочтения какому-либо одному типу разметки»*, но Schema.org рекомендован как *«более современный, полный и активно развивающийся стандарт»*.
- Разметка **не влияет напрямую на ранжирование** — только на формирование расширенных сниппетов и видимость в выдаче.
- Время применения новой разметки — по официальной формулировке **около двух недель** (до появления в выдаче после переобхода).

### Поддерживаемые типы (подтверждённый список, из разных официальных страниц)

- **Organization / Address** (`supported-schemas/address-organization.html`) — данные об организации и адресе, для спецсниппетов и Яндекс.Бизнеса.
- **Product / Offer / OfferCatalog** — разметка товаров и цен; списки товаров — через `OfferCatalog` с вложенными `Offer`.
- **Recipe** — рецепты, спецсниппет только для кулинарных/food-сайтов (партнёрская программа).
- **Movie** (`movie-description.html`) — описания фильмов.
- **SoftwareApplication** — приложения/игры/программы.
- **QAPage** — вопросы-ответы для **мобильной** выдачи, в формате Schema.org или JSON-LD.
- **Essay** — рефераты и подобные работы (специфично для рунета).
- **ImageObject** — изображения (для Яндекс.Картинок).
- **VideoObject** — видео; **без микроразметки видео вообще не индексируется** в видеопоиске (важная деталь, не просто «влияет на сниппет»).
- **BreadcrumbList** (навигационная цепочка/хлебные крошки) — официально поддерживается через **JSON-LD**, обязательные поля `name`/`url`/`position`; рекомендация — не более ~3 звеньев в цепочке; **не гарантируется** появление в выдаче даже при корректной разметке.
- **AggregateRating / Rating** — рейтинг со звёздами в сниппете; официальный пост Яндекса подтверждает факт отображения (webmaster.yandex.ru/blog/reyting-organizatsii-teper-otobrazhaetsya-i-v-snippetakh-sayta), подробности полей (ratingValue/ratingCount) — из вторичных источников, не проверено напрямую первоисточником с указанием точных property-имён.
- **Catalogs** (strict microdata) — отдельная страница `supported-schemas/catalogs` — упомянута, не фетчена подробно.

### Валидатор структурированных данных

Точный актуальный URL инструмента: **https://webmaster.yandex.ru/site/tools/microtest/** — **проверено (fetch страницы-документации `/yandex-indexing/validator.html`, которая указывает именно этот адрес)**. Также встречается более старый алиас `webmaster.yandex.ru/tools/microtest/` (без `/site/`) — вероятно, редиректит на актуальный. Функциональность: ввод URL страницы **или** вставка HTML-кода напрямую → проверка на синтаксические ошибки и соответствие требованиям именно Яндекса (не только стандарту schema.org) → вывод распознанных данных или текста ошибки.

## 10. IndexNow

### Поддержка Яндексом

**Источник:** https://yandex.ru/support/webmaster/ru/indexing-options/index-now — **проверено (fetched)**

- Яндекс официально поддерживает протокол IndexNow, разработанный совместно с Microsoft Bing, лицензия — Attribution-ShareAlike Creative Commons (IndexNow 1.0).
- Назначение: моментально уведомлять о новых/изменённых/удалённых страницах, не дожидаясь планового обхода.
- Официальная оговорка: *«Данный способ не гарантирует, что переданные страницы будут проиндексированы»* — IndexNow ускоряет **обход**, не гарантирует индексацию.
- Рекомендация: сообщать только про **новые, изменённые или удалённые** страницы — не заливать в IndexNow весь сайт сразу.

### Ключ

**Источник:** https://yandex.ru/support/webmaster/ru/indexnow/key — **проверено (fetched)**

- Ключ: только `a-z`, `A-Z`, `0-9`, `-`; длина **8–128 символов**; кодировка UTF-8.
- Файл ключа — **TXT** (или иной текстовый формат без HTML-разметки).
- Размещение:
  1. **В корне сайта** (рекомендуемый вариант) — имя файла **строго равно значению ключа** с расширением `.txt`. Пример: ключ `EdD8dkmdNLlxREi2LkhJjYOH2kyQbJqM3cBKT5fX` → файл `https://www.example.org/EdD8dkmdNLlxREi2LkhJjYOH2kyQbJqM3cBKT5fX.txt`.
  2. **В произвольном каталоге** — тогда обязательно передавать `keyLocation` в каждом запросе; файл в этом случае действителен **только** для URL из того же каталога, где лежит файл.

### API / протокол Яндекса

**Источник:** https://yandex.ru/support/webmaster/indexnow/reference/get-url.html — **проверено (fetched)**

- **GET** (один URL): `GET https://yandex.com/indexnow?url=<url>&key=<key>&[keyLocation=<url>]` — `url` должен соответствовать RFC 3986.
- **POST** (массовая отправка) на `https://yandex.com/indexnow`, тело JSON:
```json
{
  "host": "www.example.com",
  "key": "EdD8dkmdNLlxREi2LkhJjYOH2kyQbJqM3cBKT5fX",
  "keyLocation": "https://www.example.com/myIndexNowKey63638.html",
  "urlList": ["https://www.example.com/url1", "..."]
}
```
- Лимит — **до 10 000 URL за один запрос**.
- Коды ответа: `200 OK` (успех), `202 Accepted` (ключ ожидает проверки), `400` (некорректные параметры тела), `403` (ключ не подходит/невалиден), `422` (ошибки валидации — например, URL не с того хоста, что host/key), `429 Too Many Requests` (превышена частота).
- Rate limits: жёсткого лимита «запросов в день» в первоисточнике **не зафиксировано явно** — по вторичным источникам (devaka.info, utlab.ru — не первоисточники) упоминается ориентир «не чаще одного и того же URL раз в 10 минут» и практический дневной ориентир ~10 000 URL, но это **не подтверждено официальной страницей Яндекса дословно** — трактую как правдоподобную, но не первоисточную оценку.
- Поддерживается отправка URL, отдающих **404/410/301/302** — то есть IndexNow используется в том числе для сообщения об **удалении** страниц.

### Официальный протокол indexnow.org

**Источник:** https://indexnow.org/documentation — **проверено (fetched)**

- Совпадает по механике с описанием Яндекса (GET для одного URL, POST с JSON для пакета, тот же набор полей `host`/`key`/`keyLocation`/`urlList`, тот же лимит 10 000 URL/запрос, тот же формат ключа 8–128 символов из `a-zA-Z0-9-`).
- Формулировка endpoint — `https://<searchengine>/indexnow` — то есть у каждого поддерживающего протокол поисковика свой хост эндпоинта (для Яндекса — `yandex.com/indexnow`; аналогично у Bing/Naver/Seznam/Yep — свой домен), но опубликовать ключ-файл нужно один раз на сайте, а не по одному под каждый поисковик — механизм именно на этом и построен (**один ключ — рассылка нескольким API одновременно**).

### Поддержка Google (сентябрь 2026)

- **Google IndexNow не поддерживает** по состоянию на 2026 год. Вторичный источник (pressonify.ai, февраль 2026): *«Google does not support IndexNow as of February 2026 — despite testing it since October 2021»*, и что Google лишь «мониторит» протокол, не беря обязательств. **Официального заявления от самого Google в рамках этого исследования не нашлось** (не первоисточник, а SEO-агрегатор) — но многочисленные независимые источники 2026 года консистентно подтверждают статус «не поддерживается», включая нейтральные сравнительные материалы (indexnowtool.com — список поддерживающих: Bing, Yandex, Naver, Seznam, Yep — Google в списке отсутствует). Для индексации в Google рекомендуются альтернативы: Sitemaps, Search Console «Request Indexing», Google Indexing API (последний — формально ограничен JobPosting/BroadcastEvent по документации Google, что здесь отдельно не проверялось, т.к. вне периметра задачи про Яндекс).

## 11. Turbo-страницы

**Источник:** https://webmaster.yandex.ru/blog/yandex-stops-supporting-turbo-technology — **проверено (fetched напрямую)**

- Официальное объявление о **прекращении поддержки** технологии Турбо: **7 февраля 2025, 10:05**.
- Срок отключения — **два месяца** с момента объявления, то есть фактически начало апреля 2025.
- Причина (формулировка Яндекса): скорость мобильных сетей выросла, разработка мобильных версий стала доступнее и проще, у многих компаний уже есть мобильные версии сайтов и собственные приложения — технология (представленная более 7 лет назад) утратила изначальную актуальность.
- Судьба существующих Турбо-фидов: ничего вручную удалять не нужно, раздел «Турбо-страницы» в Вебмастере отключился автоматически по истечении срока; ссылки в выдаче, которые ранее вели на Турбо-версии, заменяются на **редирект 301 на оригинальные страницы сайта**.
- Рекомендации вебмастерам на переходный период: не удалять фиды самостоятельно, заменить внутренние ссылки на Турбо-страницы прямыми ссылками на оригинал, вкладываться в оптимизацию обычной мобильной версии.

**Вывод для шаблона**: технология полностью выведена из эксплуатации ещё в 2025 году, по состоянию на сентябрь 2026 — почти полтора года как отключена. **В шаблон закладывать не нужно** ни в каком виде (ни фиды, ни упоминания в доках/скиллах).

## 12. Обход по счётчику Метрики, «Скорость сайта», мобильная пригодность

### Обход по счётчику Яндекс.Метрики

**Источник:** https://yandex.ru/support/webmaster/ru/indexing-options/link-metrica — **проверено (fetched)**

- Счётчик Метрики — один из источников, по которым робот узнаёт об URL сайта; включение опции ускоряет обнаружение/индексирование страниц, где стоит счётчик.
- Настройка в три шага: 1) в Вебмастере **Настройки → Привязка к Яндекс Метрике** → «Добавить счётчик» (номер счётчика должен быть привязан к тому же сайту в самой Метрике); 2) подтверждение владельцем счётчика на стороне Метрики (сверка домена без учёта протокола/www); 3) включение непосредственно обхода — **Индексирование → Обход по счётчикам**.
- После включения робот может **временно приостановить обход** для «проверки»; рекомендуется дополнительно вести Sitemap и явно закрывать непубличные страницы от индексации (счётчик не должен «протаскивать» приватные разделы в индекс).

### «Скорость сайта»

Смешанная картина по терминологии, два разных механизма нашлись:
1. **Индекс скорости сайта** (оценочный, потребительский) — согласно вторичным источникам, показывает скорость загрузки в Яндекс.Браузере по обезличенным данным пользователей, переходящих из мобильного поиска. Отдельной детально зафетченной официальной страницы под этот конкретный индекс в рамках сессии не найдено — **средняя степень доверия**, синтез из WebSearch-сниппетов (webmaster.yandex.ru/blog/novoe-dostizhenie-skorost-sayta).
2. **«Скорость обхода»** (crawl rate, техническая настройка для робота, не про UX) — https://yandex.ru/support/webmaster/ru/service/crawl-rate — **проверено фетчем напрямую**: это замена Crawl-delay (см. п.2), не имеет отношения к Core Web Vitals.
- **Официального аналога Core Web Vitals у Яндекса нет.** Консолидированный вывод по нескольким независимым SEO-источникам (не первоисточник, но единодушны): Яндекс не публикует пороги скорости и не комментирует прямую связь скорости страницы с позициями в ранжировании; вместо этого действует через поведенческие факторы (медленная страница → выше отказы → это уже влияет на ранжирование опосредованно). Рекомендация индустрии — ориентироваться на Google PageSpeed Insights/Core Web Vitals как на основной инструмент, а «Скорость сайта» в Вебмастере использовать как дополнительную сверку. Это **разумное практическое заключение, но не подтверждено официальной формулировкой самого Яндекса** («у нас нет аналога CWV») — Яндекс просто нигде не публикует такой аналог, что подтверждается отсутствием находок при целевом поиске.

### Мобильная пригодность

- В Вебмастере есть разделы **«Диагностика сайта»** и **«Проверка мобильных страниц»** — можно проверить как отдельную страницу, так и весь сайт на адаптивность.
- Критерий, явно упомянутый в найденных сниппетах: наличие корректного `viewport`.
- Отдельно: Яндекс убрал в выдаче метку «мобильная версия» (webmaster.yandex.ru/blog/yandeks-ubiraet-metku-mobilnaya-versiya) — вторичное подтверждение, что адаптивность стала базовым ожиданием, а не отличительным дополнительным сигналом.
- Прямых fetch-подтверждений точного текущего URL раздела «Проверка мобильных страниц» в рамках сессии не получено — **пробел, требует отдельной точечной проверки**, если понадобится ссылка именно на этот инструмент.

## 13. Верификация робота Яндекса (для whitelist в CrowdSec/Traefik)

**Источник reverse DNS:** https://yandex.ru/support/webmaster/ru/robot-workings/check-yandex-robots — **проверено (fetched напрямую)**

### Метод (официальный, для скриптовой проверки)

1. Взять IP из логов сервера для интересующего User-Agent.
2. **Reverse DNS** запрос по этому IP → получить hostname.
3. Проверить, что hostname оканчивается на один из доменов: **`yandex.ru`, `yandex.net` или `yandex.com`** — дословно: *«Имена всех роботов Яндекса заканчиваются на `yandex.ru`, `yandex.net` или `yandex.com`»*.
4. **Forward DNS** запрос по этому hostname → полученный IP должен совпасть с исходным IP из логов. Если не совпадает — hostname поддельный (спуфинг под YandexBot).
- Альтернатива — встроенный веб-инструмент **«Проверка IP-адреса»** в Вебмастере (принимает IP, отвечает, принадлежит ли Яндексу).

### Диапазоны IP

- Официальная страница со списком: **https://yandex.ru/ips** — **проверено (fetched напрямую)**. Содержит:
  - **15 диапазонов IPv4** в CIDR-нотации (примеры из фетча: `5.45.192.0/18`, `77.88.0.0/18`, `95.108.128.0/17` и другие — полный список не транскрибирован в этом отчёте, страница живая и короткая, проще получить его прямым запросом в момент интеграции).
  - **1 диапазон IPv6**: `2a02:6b8::/29`.
  - Страница отдаёт **только сырой список**, без пояснений по назначению/использованию для whitelisting — трактовка (whitelist/rate-limit exemption) остаётся на усмотрение интегратора.
- Отдельно упомянуты в документации по проверке робота **автономные системы (AS)**: **AS13238, AS208722, AS212066** — и явная оговорка, что *«IP-адреса... часто меняются, поэтому их список не разглашается»* в смысле детального перечня под каждый конкретный суб-сервис робота — то есть страница `yandex.ru/ips`, видимо, даёт агрегированные диапазоны всей сети Яндекса (включая не только поискового робота), а не только «пул адресов краулера» с гарантией полноты и неизменности.

### Рекомендация для CrowdSec/Traefik whitelist

Наиболее надёжный вариант — **не жёсткий IP-whitelist**, а связка «глядя на User-Agent → делать reverse+forward DNS проверку» (то, что рекомендует сам Яндекс), поскольку IP-диапазоны сети Яндекса шире, чем только робот, и могут меняться. Список `yandex.ru/ips` можно использовать как **быстрый первичный фильтр** (снизить нагрузку на rate-limiter/CrowdSec для трафика с этих подсетей), но не как единственный источник правды для «это точно поисковый робот» — тем более что CIDR-список датирован моментом обращения и не является контрактной гарантией на будущее (сам Яндекс так и пишет — «часто меняются»).

## 14. Sitemap у Яндекса

**Источники:** https://yandex.ru/support/webmaster/ru/controlling-robot/sitemap — **проверено (fetched напрямую, самый полный)**; https://yandex.ru/support/webmaster/ru/indexing-options/sitemap.html — тот же контент, дублирующий путь.

- **Лимит URL на файл**: **50 000**. Больше — использовать **sitemap index** файл, в котором можно перечислить до 50 000 файлов sitemap (тот же лимит рекурсивно применяется к самому индекс-файлу).
- **Лимит размера**: **50 МБ в несжатом виде** — как на обычный sitemap, так и на индекс-файл.
- **Длина одного URL**: суммарно **2048 символов**, из них до **1024 символов на доменное имя** (например, `https://site.com`), оставшиеся до **1024 на путь**.
- **Форматы**: **XML и TXT**. Поддержка gzip-сжатия и RSS/Atom-фидов **не подтверждена и не упомянута** в зафетченном тексте — трактовать как «не гарантировано», хотя многие другие поисковики (в т.ч. сам протокол sitemaps.org) gzip поддерживают.
- **Теги внутри XML**:
  - `loc` — обязателен.
  - `lastmod` — опционален, максимум 100 байт; используется как сигнал даты последнего изменения.
  - `changefreq` — опционален, максимум 100 байт.
  - `priority` — опционален, число от `0.0` до `1.0`, значимость страницы.
  - Неизвестные/неподдерживаемые элементы робот **игнорирует**, не считает ошибкой.
- **hreflang/xhtml:link внутри sitemap** — **явно не упомянуто** ни на одной из зафетченных страниц. Это отличается от Google, который официально поддерживает `xhtml:link rel="alternate" hreflang` прямо в sitemap. Для Яндекса — **не подтверждено первоисточником**, соответственно в SSR-шаблоне полагаться на этот механизм для Яндекса не стоит; hreflang приоритетнее класть в `<head>`/HTTP Link, а не в sitemap, если целевой поисковик — Яндекс.
- **Кодировка**: UTF-8; кириллические URL распознаются и в percent-encoded виде, и в «сыром» виде.
- **Домен**: sitemap должен ссылаться только на страницы **того же домена**, на котором сам лежит; кросс-доменные sitemap не предусмотрены.
- **Ответ сервера**: при запросе файла sitemap сервер должен отвечать **200 OK**.
- **Объявление о sitemap**: два способа — указать `Sitemap:` в robots.txt **и/или** добавить файл в разделе «Файлы Sitemap» Яндекс.Вебмастера (можно оба одновременно, не взаимоисключающе).

## 15. Верификация сайта в Вебмастере

**Источники:** https://yandex.ru/support/webmaster/ru/service/rights.md — **проверено (fetched, самый подробный)**; https://yandex.ru/dev/webmaster/doc/ru/concepts/verification — **проверено (fetched, API-вариант)**.

### Способы (равнозначны между собой)

1. **HTML-файл в корне сайта** — файл с уникальным именем вида `yandex_<код>.html`, содержащий только заданный код (без лишнего контента). Доступен по `//example.com/yandex_XXXXXXXXXXXXXXXX.html`. Если сайт слушает и на IPv4, и на IPv6 — нужно убедиться, что файл отдаётся по обоим.
2. **Мета-тег на главной странице**, строго внутри `<head>`:
```html
<meta name='yandex-verification' content='XXXXXXXXXXXXXX' />
```
Размещение вне `<head>` не работает; подтверждение может занимать несколько минут.
3. **DNS TXT-запись**: запись типа TXT с уникальным значением вида `yandex-verification: <код>`. Важно: адрес сайта в Вебмастере должен буквально совпадать с адресом в DNS — `www.example.com` и `example.com` для Яндекса **разные сайты**. DNS-записи могут применяться дольше остальных способов.
4. **Через Яндекс Тег Менеджер (YTM)** — без правки исходного кода: раздел «Тег Менеджер → Теги» → шаблон «Яндекс Вебмастер» → вставить код подтверждения → триггер «Инициализация» → опубликовать.
5. **Через Google Tag Manager (GTM)** — аналогично: импортировать шаблон тега «Official Yandex Webmaster», вставить verification ID, триггер «Initialization — All Pages», опубликовать.
6. Дополнительно (бета) — **через регистратора домена** (для поддерживаемых регистраторов, автоматическое предложение) — применяется от 10 минут до 24 часов.

Проверка подтверждения самим Яндексом может занимать **до 24 часов**.

### API-вариант (программная верификация)

https://yandex.ru/dev/webmaster/doc/ru/concepts/verification — 3 шага:
1. `GET https://api.webmaster.yandex.net/v4/user/{user-id}/hosts/{host-id}/verification` → получить `verification_uin` (код).
2. Разместить код одним из трёх способов — **DNS**, **HTML_FILE** или **META_TAG** (те же самые механики, что и в UI, включая точный формат HTML-файла с `<meta http-equiv="Content-Type" content="text/html; charset=UTF-8">` в `<head>` и текстом `Verification: <код>` в `<body>`).
3. `POST https://api.webmaster.yandex.net/v4/user/{user-id}/hosts/{host-id}/verification?verification_type=<DNS|HTML_FILE|META_TAG>` → запускает саму проверку.

### Рекомендация для SSR-шаблона (TanStack Start за Traefik, без CDN)

Из всех способов удобнее всего зашить через **env** именно:
- **Мета-тег** (`yandex-verification`) — тривиально прокинуть значение из `window.__APP_CONFIG__`/рантайм-конфига в `<head>` на этапе SSR-рендера (аналогично тому, как в проекте уже прокидывается `SENTRY_DSN` через runtime config, см. `.claude/rules/env-local.md` этого репозитория) — не требует отдельного файлового роута.
- Альтернатива — **HTML-файл**: для Node/SSR-сервера это означает завести отдельный статический роут `/yandex_<код>.html`, отдающий текст из env — чуть больше работы, чем один мета-тег, но не требует пересборки при смене кода подтверждения (если код читается в рантайме).
- **DNS TXT** — не зависит от приложения вообще (настраивается на уровне DNS-провайдера), но тогда это вне зоны ответственности SPA/SSR-шаблона и не требует изменений в коде — просто фиксируется как рекомендация в доке `docs/reference/deployment.md` или `env-local.md`, а не как параметр приложения.

Итог: **мета-тег через env — самый естественный вариант именно для SSR-шаблона** (одна переменная окружения → один условный `<meta>` в корневом layout), DNS TXT — самый «чистый» вариант, но целиком вне кода приложения.

## Ключевые пробелы / что не удалось подтвердить первоисточником

1. Полный enum значений переключателя «Рендеринг JS» в Вебмастере (кроме дефолтного «на усмотрение робота») — в документации не перечислен.
2. Точная трактовка Яндексом 5xx именно **на сам файл robots.txt** (в отличие от 4xx, которое подтверждено дословно комментарием сотрудника) — есть только по аналогии из общих практик.
3. Официальное заявление Яндекса (не форумы/блоги третьих лиц) об изменении трактовки `rel=nofollow` в части передачи веса — не найдено; возможно, такого отдельного заявления вообще не было, и это домысел индустрии по аналогии с Google.
4. Актуальная (после 2013 года) официальная страница именно про hreflang в новой структуре доков `/support/webmaster/` — не найдена; вероятно, тема поглощена регионалностью.
5. Официальная страница Яндекса с явным перечнем свойств `AggregateRating`/`Rating` (ratingValue/ratingCount и т.п.) — не зафетчена напрямую, взято из вторичных источников.
6. Поддержка gzip-сжатия и hreflang-разметки внутри sitemap.xml Яндексом — ни подтверждена, ни опровергнута прямой формулировкой (эти опции просто не упомянуты на официальных страницах, что стоит трактовать консервативно как «не гарантировано»).
7. Официальный, дословный rate-limit IndexNow «в день» от самого Яндекса (не только «10 000 URL за раз») — не подтверждён первоисточником.

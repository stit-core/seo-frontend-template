# Skill: plan

Единый план активной работы. Любое содержательное изменение идёт через секцию
здесь — план переживает `/clear`, виден тимейтам, фиксирует «зачем» и «что
будет сделано».

## Когда применять

- «давай сделаем X» (где X — не truly-atomic правка)
- Рефакторинг затрагивает несколько слайсов
- Новая фича / новая page / новый widget
- Миграция (зависимость, API, конвенция)

## Когда НЕ применять

- Truly-atomic фикс: typo, исправить ошибку в одном файле без архитектурного решения
- Багфикс с RED-first тестом — там просто пишем тест → фикс → коммит
- Эксплоративные вопросы («что такое X?») — это разговор, не работа

## Структура секции

```markdown
## Active

### <короткое имя плана>

**Цель**: одно предложение — зачем.

**Контекст**: что в репо сейчас, что мешает достичь цели (1-2 предложения).

**Шаги**:
1. _действие_ — _ожидаемый результат_
2. _действие_
3. _действие_

**Гейт**: что должно быть зелёным перед claim «готово» (обычно `pnpm check`,
плюс конкретные тесты).

**Открытые вопросы**: что ещё нужно согласовать с юзером (если есть).
```

## Workflow

1. Создать секцию в `.claude/plans/roadmap.md` под `## Active` (или обновить
   существующую)
2. Если шагов больше 3 — параллельно создать `TaskList` через `TaskCreate`
3. По мере прогресса — отмечать шаги в roadmap (`[x]` / удаление) и обновлять
   TaskList
4. По завершении — **удалить `### <план>`-секцию целиком** из `## Active`.
   История — в `git log` (forward-only, без архива в артефакте). Незакрытый
   follow-up из закрытой задачи — отдельной строкой в `## Backlog`, а не
   переездом самого закрытого плана

## Anti-patterns

- ❌ Планировать «всё сразу» — секции должны быть размером в 1-3 дня работы
- ❌ Дублировать roadmap и TaskList — TaskList для тактики, roadmap для стратегии
- ❌ Не обновлять roadmap при изменении подхода — план должен отражать реальность
